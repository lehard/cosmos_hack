# Документы по этапам процесса

Какие документы система собирает из истории изделия, кто и как их подписывает, что уходит наружу. Опоры: AD-12, AD-13, AD-43, AD-11, AD-17, AD-19; FR-54, FR-65, FR-66, FR-69, FR-139, FR-145; PRD §11.16; раздел спайна «Каталог документов по этапам»; критерии О1, О2, Т3.

**Статус.** Уровни подписи и маршруты — из спайна (они сильнее входного каталога процессной сессии, где колонка уровней устарела) и сверены с шаблонами: где шаблон есть, таблицы ниже совпадают с ним (раздел «Сверено с кодом»). Колонка «Нормативная основа / форма» взята из входного каталога документов по этапам; где формы нет или она у каждого предприятия своя, так и сказано. Шаблоны и поля документов строят эпики 28 и 44; код — модуль `documents` (`backend/internal/domain/documents`, `backend/internal/application/documents`), шаблоны и маршруты — `normative/documents/templates.v1.yaml`.

## 1. Как устроен документ

- **Документ — детерминированная проекция журнала** (AD-12): шаблон шага@версия (нормативный слой) × события-источники. Документ не редактируется: новая версия — новый отпечаток; подписи прежней версии остаются при ней. Дописывание следующим подписантом — отдельный связанный документ со ссылкой на отпечаток предыдущего.
- **Отпечаток.** `content` = JCS(данные без `rendering_hash`); `rendering_hash` = H(отрисовка(шаблон@версия, content)); `doc_digest` = H(JCS(content ∪ `rendering_hash`, `template_ref`, `doc_format_version`)); H — Стрибог-256 (формат цепочки, [data-model.md](data-model.md)). Поля краткой сводки для подписи уровня 2 перечислены в шаблоне и входят в отпечаток.
- **Жизненный цикл — только события:** `document.version.drafted` (реакция движка или команда человека — «Запросить решение», выдача прав) → подписи `document.signature.recorded` → `document.route.closed` → `document.version.annulled` новой записью. Документы вне изделия (политика, ключи, версия процесса, смена, партнёр) — потоки объектов межизделийной стадии.
- **Отрисовка** — каноническая HTML; серверного PDF нет. Печатная рамка (QR `ant:doc:‹id›:‹doc_digest›`, дата печати, колонтитул «получено из системы») в отрисовку не входит. Бумажный экземпляр имеет свой статус (напечатан / подписан / уничтожен) — событием; журнал не трогается.
- **«Документов собрано из истории — вручную не понадобилось»** — счётчик у каждого изделия в проекции документов (FR-65).
- Агент токена, сервер и `demo-signer` собираются из одного коммита: отпечаток документа считает пакет `domain/documents`, отпечаток подписываемой записи — пакет `domain/signing`, общий для всех трёх; `make check` сверяет отпечатки сервера с эталонными документами, а агента — с отпечатком сервера над той же записью.

### 1.1. Классы документов

| Класс | Что это | Подписи |
|---|---|---|
| **Запись** | генерируется из журнала по шаблону | по маршруту шаблона |
| **Решение** | черновик + маршрут подписей; «генерирует» значит «готовит черновик», решает человек | по маршруту, вычисленному `RequiredApprovals` |
| **Требование** | ссылка с версией (КД, ТУ, МК, план контроля, разрешение на отступление) | в составе нормативного слоя |
| **Вход** | внешняя запись: протоколы КИМ, заключения НК, наряды MES и 1С, сертификаты и выписки поставщиков | проверяем чужую подпись, если она есть |

### 1.2. Уровень подписи и маршрут

**Уровень** определяет, как собирается одна подпись (AD-13, PRD §11.16):

| Уровень | Что подписывается | Как |
|---|---|---|
| 0 | сообщение устройства | ключ устройства в edge-агенте |
| 1 | только факты исполнителя и физические подтверждения мастера: начал, закончил, переместил, запросил контроль, сообщил о подозрении на дефект, нанёс или снял носитель | личный ключ без дополнительных окон; перечень вкомпилирован в агент токена, всё прочее агент отклоняет сам |
| 2 | «годен» контролёра, все заключения ОТК, все критические действия | доверенное отображение сводки 3–7 полей и явное подтверждение; допускается пачка («подписать: N изделий, операция X, годен» — одно окно, одно касание токена) |
| 3 | сменный рапорт | одна подпись над корнем дерева Меркла (RFC 6962) по локальному журналу агента |

**Маршрут** определяет, кто, сколько и в каком порядке подписывает: этапы по порядку; в этапе — полномочие и, для действий контроля, действующее цифровое клеймо; «1 / все / k из n»; заместитель по делегированию; уровень; разделение обязанностей; эскалация на k-м предъявлении и по сроку; внешняя сторона (партнёр, ВП); допуск бумаги. Маршрут хранится в шаблоне документа в нормативном слое.

### 1.3. Обязательные подписи — одна функция

`domain/access.RequiredApprovals(маршрут шаблона, контекст решения, политика@basis)` возвращает этапы (AD-43). Её вызывают `documents` при черновике, `api` — для объяснения прав и «Запросить решение», верификатор — при проверке. Набор вычисляется один раз при `document.version.drafted` и входит в канонический JSON документа: подписант видит, кто ещё подписывает. «Маршрут закрыт» — только реакция `document.route.closed` модуля `documents` после проверки каждой подписи (над текущим отпечатком; полномочие и клеймо подписанта на её `seq`; разделение обязанностей). Модули-исполнители действуют только по этой реакции.

### 1.4. Бумага с заверением

Бумага — второй равноправный путь подписи (FR-139) и всегда подпись двух людей: подписант ставит подпись ручкой на распечатке с QR (отпечаток и ожидаемый подписант этапа); скан загружает и заверяет своей цифровой подписью уровня 2 второй человек с допуском и ролью, стоящий над процессом или рядом с ним. Заверитель задаётся свойством шага BPMN, для документов вне шага — этапом `attester` маршрута; не задан — бумага на этапе запрещена. Заверитель ≠ подписант. Запись хранит подписанта, заверителя и учётный номер бумажного оригинала в архиве ОТК; запись критического действия фиксирует обоих. Скан с чужим QR-отпечатком не принимается. Бумажные подписи не входят в сменный рапорт — их покрывают подпись заверителя и реестр бумажных решений у верификатора.

## Сверено с кодом

- События документа (`contracts/events/catalog.yaml`, раздел `document`, владелец схемы — `documents`): `document.version.requested` («Запросить решение», выдача прав), `document.version.drafted`, `document.signature.recorded`, `document.signature.declined` (подписант не согласовал), `document.route.closed`, `document.version.annulled`, `document.paper.status_changed` (статус бумажного экземпляра). Имена в разделе 1 — фактические.
- Шаблоны — один файл `normative/documents/templates.v1.yaml` (схема `contracts/normative/templates.schema.json`): 39 шаблонов, из них 26 полных (маршрут `route`, поля сводки уровня 2 `summary`, отрисовка `layout`) и 13 только объявлены — журналы и протоколы ВК, требование-накладная, накладная между цехами, журналы сварки, спецпроцесса и затяжек, карта сборки, протокол герметичности, внешний вход (`cmm-protocol`, `ndt-conclusion`, `test-program`). Полные: позвоночник эпика 28 — `traveler`, `nc-statement`, `nc-disposition`, `process-version-approval`, `decision-request`; каталог эпика 44 — `incoming-inspection-act`, `lot-conformity-label`, `item-tag`, `first-article-act`, `presentation-log`, `route-sheet`, `intervention-record`, `customer-presentation-notice`, `customer-conclusion`, `acceptance-certificate`, `passport`, `isolator-log`, `nc-label`, `scrap-act`, `concession`, `passport-extract`, `device-commissioning-act`, `restore-act`, `partner-registration-act`; эпик 26 — `policy-grant`, `controller-assignment`. Построитель содержимого (`doc_type`) — `traveler`, `nc_statement`, `nc_disposition`, `event_record` (документ по событию-триггеру свёртки), `generic` (по запросу).
- Маршруты сверены с шаблонами; таблицы раздела 2 приведены к ним: акт ВК — + мастер склада; бирка — уровень 1 по источнику; журнал предъявления — предъявивший (1) → контролёр (2); решение по НП — этапы по варианту решения и приёмке заказчика; акт о браке — без комиссии в обязательном минимуме; акт ввода устройства — два этапа. Паспорт и свидетельство о приёмке — два шаблона: `acceptance-certificate` (начальник ОТК → руководитель производства → представитель заказчика) и `passport` (начальник ОТК → представитель заказчика). Подпись ключа шлюза у выписки паспорта ставит модуль `federation` при отправке, не маршрут шаблона.
- Шаблона нет, остаётся описанием: решение комиссии по специальному процессу, журнал регистрации несоответствий, план корректирующих мер, уведомление партнёру. Акт генезиса, сменный рапорт, выдача и отзыв ключа, паспорт допуска анализатора и возврат анализатора — не шаблоны документов, а записи журнала (`journal.genesis.recorded`, `key.shift_report.recorded`, `key.registration.recorded`, `key.revocation.recorded`, `analyzer.passport.admitted`, `analyzer.passport.reinstated`). Шаблон `restore-act` есть и оформляется запросом, но кода, который пишет `journal.restore.recorded`, нет — акт восстановления остаётся описанием ([backup-restore.md](backup-restore.md)).
- Эталонные документы — `contracts/crypto/test-vectors/documents.v1.json` (шаблон, канонический `content`, отрисовка HTML, `rendering_hash`, `doc_digest`, QR) для `traveler@1`, `nc-statement@1`, `nc-disposition@1`; тест `backend/internal/application/documents/golden_test.go` (в `make check`) требует байт в байт совпадения при сборке (`Compose`) и пересчёте (`Rebuild`). Пример — сопроводительная карта `TRV-ENT01:FL-0007` (`traveler@1`), `doc_digest` = `streebog256:ef9068f8176be53f81c6becddc2e554fefdc7883659c9a6bd5399842ef835c92`, QR `ant:doc:TRV-ENT01:FL-0007:‹doc_digest›`. Агент токена сверяет свой отпечаток с сервером над подписываемой записью (`backend/cmd/token-agent/internal/agent/agent_test.go`, пакет `domain/signing`); файл эталонных документов читает только серверный тест.
- Документы шагов в `normative/process/flange-process.bpmn` — элементы `ant:document/@template`, ЗТ — `ant:properties/@closingPoint`: ЗТ-1 (`V3`) — акт ВК, журнал результатов ВК, ярлык партии; ЗТ-2 (`M4`) и ЗТ-3 (`W5`) — журнал предъявления, сопроводительная карта; ЗТ-4 ч.1 (`A3`) — карта сборки; ЗТ-4 ч.2 (`A9`) — журнал предъявления, карта сборки, запись вмешательства; ЗТ-5 (`T2`) — протокол испытаний; ЗТ-6 (`K3`) — журнал предъявления, извещение ВП, свидетельство о приёмке; ЗТ-Р (`N2` подпроцесса Н) — заявление о несоответствии, решение по НП, акт о браке. Вне ЗТ: акт первой детали — на мехобработке `M1`, маршрутный лист — на отправке и приёмке цехом, паспорт — на сдаче на склад `K4`, журнал изолятора и ярлык «Брак» — на изоляции `N1`, разрешение на отклонение — `N3`. Извещение ВП в BPMN стоит только на ЗТ-6; шаблон оформляет его на любом предъявлении представителю заказчика.
- Бумажные подписи: подписант, заверитель (`attested_by`) и учётный номер оригинала (`paper_original_no`) хранятся в записи `document.signature.recorded` и в проекции документа (`backend/internal/domain/documents/model.go`, тип `Signature`); скан — в хранилище материалов. Реестр бумажных решений — поле `paper_register` отчёта верификатора (`contracts/internal/verifier/report.v1.json`) и `paper_decisions` его представления в API (`backend/internal/application/security/views.go`, тип `VerifierReport`); верификатор пока оставляет реестр пустым и считает бумажные подписи только счётчиком класса `paper` — наполнение реестра остаётся описанием.
