# Как подключить новый адаптер без переписывания ядра

Ответ на требование FR-114 («новый источник, адаптер или генератор предложений подключается без переписывания
бизнес-логики ядра; приложены конфигурация и пример подключения»), кейс §3.1 и критерий О6. Пример — адаптер
**Галактика ERP**: второй получатель того же внутреннего сигнала, что уходит в 1С (FR-92, эпик 31).

**Опоры:** AD-1, AD-18, AD-20, AD-35 (`architecture-spine.md`); FR-90…96, FR-111, FR-114; обзор интеграций —
[integrations/README.md](integrations/README.md).

Имена: платформа для людей — **Главный**; техническое имя в коде, конфигурации и путях — `ant` (Д-65).

## 1. Что такое адаптер в Главном

Ядро говорит с внешним миром только через **порты на нашем языке** (AD-18, AD-35). Адаптер — реализация
порта в `backend/internal/infrastructure/integration/‹модуль›/‹система›`; внешний формат не выходит за его
пределы. Поэтому новая система — это новый пакет рядом, а не правка правил.

| Порт (слой `application`) | Что говорит ядро | Адаптеры | Общий контрактный тест |
|---|---|---|---|
| `erp.Ledger` — порт учёта | наружу: «принято в работу», «смена склада», «перевод в брак», «возврат поставщику», «возврат из брака», «выпуск», «результат контроля»; внутрь: задания, номенклатура, партии, соответствия ID | `erp/onec` (1С, OData + HTTP-сервис `qc.v1`), `erp/galaktika` (XML-пакет и REST-фасад `gal.qc.v1`) | `application/erp/ledgertest` |
| `mes.Channel` — канал MES | наружу: блок и снятие блока изделия или партии; внутрь: задания и события операций | `mes/b2mml` (подмножество B2MML-JSON `mes.isa95.v1`) | контрактный тест адаптера |
| `cad.Reader` — состав изделия | сборка: позиции, количества, связи, характеристики; `geometry: null` явно | `cad/kompas` (файл условной сборки) | контрактный тест адаптера |

Что при подключении нового адаптера **не меняется**: домен (`backend/internal/domain/*`), сценарии приложения
(роль `outbox`, реакция «учётное сообщение сформировано», шлюз входящих, проекции и операции API), контракт
событий `contracts/events`, журнал, интерфейс. Меняются: новый пакет адаптера, его контракт в
`contracts/integrations`, одна фабрика в сборке зависимостей `cmd/ant` и ключи конфигурации.

## 2. Пример по шагам: Галактика как второй получатель порта учёта

### Шаг 1. Контракт внешней системы — `contracts/integrations/erp/galaktika/`

Контракт — источник правды (AD-20), рядом с кодом не дублируется:

- `gal.qc.v1/*.schema.json` — JSON Schema сообщений (пакет, квитанция, описание ответной стороны, входящие);
  диалект и линтер — общие для всех схем (`contracts/scripts/check.sh`);
- `gal.qc.v1.xsd` — та же модель для обработчика на стороне Галактики (XML-пакет каталога обмена);
- `examples/` — эталонные сообщения: XML и JSON одного пакета, исходящие, квитанции, ошибка;
- `README.md` — транспорты, словарь «порт → система», классы ответа, сопоставление ID.

`make generate` встраивает схемы и эталоны в сборку (`backend/internal/contracts/schemas`), и адаптер
проверяет сообщения тем же валидатором, что приём (`infrastructure/integration/schemacheck`).

### Шаг 2. Адаптер — реализация порта

`backend/internal/infrastructure/integration/erp/galaktika`:

```go
// Адаптер реализует порт учёта — компилятор проверяет это при сборке.
var _ app.Ledger = (*Client)(nil)

func (c *Client) Info() app.LedgerInfo                                   // система, адрес, stand, версия контракта
func (c *Client) Check(ctx context.Context) (app.Checked, error)         // сверка ответной стороны (about)
func (c *Client) Post(ctx context.Context, m app.Outgoing) (app.Response, error)
func (c *Client) Pull(ctx context.Context) ([]app.Inbound, error)       // задания, партии, каталог МЦ
```

Обязательства адаптера перед ядром (одинаковы для любого получателя):

| Правило | Как сделано у Галактики |
|---|---|
| Перевод на границе | `Encode` строит пакет `GalExchange` из `app.Outgoing`; `Inbound` строит факты `erp.*` и `reference.external_id.mapped` из пакетов Галактики |
| Проверка до отправки (FR-111, О8) | `Check(e)` — JSON-форма пакета по схеме `exchange.schema.json`; не по схеме — `ContractError{Local}`, в Галактику ничего не уходит |
| Сверка ответной стороны (AD-18) | `about` без `gal.qc.v1` среди поддерживаемых — `ContractError`, канал `degraded`, отправки нет |
| Классы ответа (FR-96) | квитанция → `accepted`, повтор номера → `duplicate` (та же квитанция), ошибка данных → `rejected` с нашим кодом из `contracts/errors.yaml`; транспорт → `TransportError` (повтор тем же номером), несовместимость → `ContractError` |
| Идемпотентность (AD-7) | номер пакета = `X-Message-Id` порта (UUIDv5 бизнес-ключа и версии); входящие `event_id` — от номера пакета Галактики |
| Внешние ID (FR-95) | только записями `reference.external_id.mapped`: `galaktika:‹база›:‹таблица›:‹NRec›` → наш ID; тип изделия — по обозначению КД (`domain/cad.ItemTypeID`), как у 1С и КОМПАС |

Транспорт — деталь адаптера и ключ его конфигурации: у Галактики их два (`exchange-dir` — XML-файлы в каталоге
обмена, `rest-facade` — JSON по HTTP), модель сообщения и порт одни.

### Шаг 3. Контрактный тест

`backend/internal/infrastructure/integration/erp/galaktika/galaktika_test.go`:

- эталоны проходят схемы; XML- и JSON-формы одного пакета совпадают; имена XML объявлены в XSD;
- эталонный внутренний сигнал порта (`ledgertest.Signals()` — по сообщению на каждое учётное действие) даёт
  эталонные пакеты;
- **общий контрактный тест порта** `ledgertest.Run` — на обоих транспортах Галактики и на stand-е 1С
  (`erp/onec/ledger_contract_test.go`): сверка, квитанция на каждое действие, повтор — та же квитанция без
  второго документа, входящие — типы порта учёта с детерминированными `event_id`, каждый факт проходит схемы
  приёма;
- классы ответа и сбои: `503` — транспорт, `422 LOT_NOT_FOUND` — `erp.id_mapping_missing`, `400
  CONTRACT_VERSION` — несовместимость, пакет не по схеме не уходит.

Ответная сторона в тесте — эталонный фасад и каталог обмена по контракту; stand Галактики со своим состоянием
и страницей — эпик 43, тем же протоколом.

```bash
# в контейнере Go (рецепт GO_RUN из Makefile); БД контрактным тестам не нужна
go test ./internal/infrastructure/integration/erp/... ./internal/application/erp/...
```

### Шаг 4. Конфигурация

Включённые системы и адреса — конфигурация (AD-18). Ключи канала Галактики (`deploy/config/ant.yaml`,
поле `ERP.Galaktika` в `cmd/internal/config`; переменные `ANT_ERP_GALAKTIKA_*`):

```yaml
integrations:
  enabled: [galaktika]            # вместо onec: какая учётная система получает сигнал порта учёта
erp:
  galaktika:
    transport: exchange-dir       # exchange-dir | rest-facade
    dir: /var/lib/ant/exchange/galaktika   # out/ ack/ in/ in-ack/ about.xml
    base_url: ""                  # для rest-facade: http(s)://‹хост›/galaktika/esb/v1
    node: ant                     # наш узел обмена
    peer: ""                      # узел Галактики; пусто — из about
    database: ""                  # база Галактики для внешних ID; пусто — из about
    enterprise: ENT01
    user: ""
    password_file: ""             # секрет — только файлом
    timeout: 10s
    poll: 1s                      # опрос очереди исходящих
    recheck: 5m                   # сверка about
    pull_every: 30s               # опрос входящих пакетов
    retry_max: 8                  # для exchange-dir: ожидание квитанции ≈ 70 мин, затем карантин
```

### Шаг 5. Подключение в сборке зависимостей

Единственное место, где адаптер встречается с ядром, — `cmd/ant` (AD-1: сборка зависимостей только в `cmd/*`).
Роль `outbox`, реакция, шлюз входящих и операции API берут порт, а не конкретную систему:

```go
// cmd/ant/outbox.go (упрощённо; в коде — ledger и galaktikaClient): фабрика порта учёта по конфигурации (1С — эпик 30, Галактика — эпик 31).
func ledger(env *environment) (erpapp.Ledger, error) {
	if slices.Contains(env.cfg.Integrations.Enabled, "galaktika") {
		c := env.cfg.ERP.Galaktika
		return galaktika.New(galaktika.Config{Transport: c.Transport, Dir: c.Dir, BaseURL: c.BaseURL, Node: c.Node,
			Peer: c.Peer, Database: c.Database, Enterprise: c.Enterprise, User: c.User, Password: secret(c.PasswordFile),
			Timeout: c.Timeout, Stand: c.Stand})
	}
	return onecClient(env)
}

// Роль outbox и реакция — без изменений, кроме источника порта:
//   ob := &erpapp.Outbox{..., Ledger: l, ...}
//   dom.Env{Topology: topo, System: l.Info().System}
```

`erpapp.Outbox` фильтрует очередь по `Ledger.Info().System`, реакция `erp.posting` помечает сообщение системой
из `dom.Env.System` — поэтому тот же сигнал `erp.posting.requested` уходит в Галактику тем же путём: очередь —
проекция журнала, повтор только при транспорте, карантин и ручная переотправка, квитанция —
`erp.posting.responded`, при воспроизведении роль не запущена.

## 3. Чек-лист нового адаптера

1. Порт уже есть? Если нет — порт объявляется на нашем языке в `application/‹модуль›`, домен не знает о системе.
2. Контракт системы — в `contracts/integrations/‹модуль›/‹система›`: схемы, эталоны, README; `contracts/scripts/check.sh` зелёный.
3. Пакет `infrastructure/integration/‹модуль›/‹система›`: `var _ app.‹Порт› = (*Client)(nil)`; проверка сообщений
   схемой до отправки; сверка ответной стороны; классы ответа; детерминированные `event_id`; внешние ID — только
   соответствиями.
4. Контрактный тест на эталонах + общий тест порта, если он есть (`ledgertest.Run` для порта учёта).
5. Ключи конфигурации и фабрика в `cmd/ant`; секреты — файлами.
6. Stand за тем же протоколом — отдельно (`…/‹система›/stand`, роль `stands`), когда нужна живая ответная сторона.
7. Документ `docs/integrations/‹система›.md`: направления, данные, шаг процесса, источник истины, ID, ошибки,
   граница эмуляции, путь к реальной системе (FR-90).

### Шаг 6. Установка конфигурацией и включение на экране «Интеграции» (FR-157, эпик 48)

Путь нового адаптера целиком: **каркас с контрактным тестом → зелёные проверки → установка конфигурацией →
включение на экране** (FR-114, AD-47).

- **Установка** — только конфигурация: система в `integrations.enabled`, адрес и секреты — в
  `deploy/config` и файлах. Режимы задаёт адрес: у 1С, Галактики и MES флаг `stand` говорит, что за
  адресом стенд (эмулятор) или реальная система; у прочих систем раздельных адресов нет. Интерфейс
  конфигурацию не меняет.
- **Включение** — стол администратора → раздел «Интеграции» → строка системы → в правом окне основание и
  «Включить» / «Выключить» / «Переключить на стенд (на реальную систему)». Решение — запись журнала
  `ops.integration.state_set` (критическое действие, администратор единолично — Д-71); без решений действует
  состояние по умолчанию профиля: в `prod` — реальная система, в `demo` и `fixtures` — стенд.
- **На лету**: роли `outbox` и приём читают состояние через порт `application/ops.IntegrationSwitch`
  (кэш — 1 с), без перезапуска. Выключенная учётная система — исходящие копятся в очереди и уходят после
  включения, входящие не опрашиваются; входящие от источников выключенной системы (`erp.‹система›`,
  `mes.*`, `cad.kompas`, `partner:*`…) и от источника, отключённого решением `ops.source.disabled`, приём
  отвергает с кодом `ingest.source_disabled` (сообщение остаётся в карантине).
- **Гард**: неустановленную систему включить нельзя (`ops.integration_not_installed`), стенд в `prod` —
  `ops.stand_forbidden`, режим без адреса — `ops.integration_mode_unavailable`.
- **«Проверить соединение»** — `ops.integration.check`: та же сверка ответной стороны, что при старте
  (порт `opsapp.Probe`, в `cmd/ant/integrations.go` — `integrationProbe`); итог — запись
  `ops.integration.checked`. Новый адаптер добавляет свою ветку в `integrationProbe` и, если у него есть
  опрос входящих, обёртку «не опрашивать выключенную» по образцу `switchedLedger`.
- **Новая система в списке** — её код в перечислениях схем `ops.integration.state_set` / `checked`
  (совместимое расширение), в `domain/ops.KnownSystems` и префиксы её источников в `systemSources`;
  название для людей — `widgets.integrations.systems.‹код›` в `frontend/src/shared/i18n/ru.shell.json`.

## 4. Другие примеры того же приёма

- **Другая MES** (1С:MES, Галактика MES, ГОЛЬФСТРИМ) — пакет `integration/mes/‹система›` за портом
  `mes.Channel`: блоки, задания и события операций на нашем языке не меняются; B2MML-адаптер — образец.
- **Прямое подключение КОМПАС** — адаптер порта `cad.Reader`: экстрактор COM API7 на Windows-шлюзе или
  выгрузка состава из ЛОЦМАН:PLM дают сборку в том же виде; перевод связей W-1, J-1, S-1 в зоны и ограничения
  делает домен `cad`, он не меняется ([integrations/kompas.md](integrations/kompas.md), §7).
- **Новый источник событий оборудования** — stand или edge-агент подаёт факты в обычный приём
  (`ingest`), схема события — `contracts/events`; ядро видит только факты.
- **Брокер сообщений вместо HTTP** — адаптер порта `Publisher` / `WorkFeed`
  ([observability-kafka-otel.md](observability-kafka-otel.md)).

## 5. Ограничение MVP

Порт учёта обслуживает **одну учётную систему на экземпляр**: `integrations.enabled` выбирает 1С или Галактику,
сигнал и его бизнес-ключ одни. Одновременная отправка одного сигнала в две учётные системы требует ключа
сообщения с системой (`‹система›:‹субъект›/‹действие›/‹точка›`) и оси «учёт» по каждой системе — это
изменение домена `erp`, оно описано, но в MVP не сделано.
