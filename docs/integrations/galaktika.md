# Интеграция с Галактика ERP

Двусторонний обмен с Галактика ERP через отдельный адаптер без изменения ядра (FR-92, кейс §3.3). В MVP — адаптер в коде, контракт `gal.qc.v1`, эталонные сообщения, контрактный тест и stand Галактики в роли `stands` (эпик 43) — обмен показывается вживую, как с 1С. Тот же внутренний сигнал порта учёта, что уходит в 1С, может уйти и в Галактику — какие системы включены, задаёт конфигурация.

**Опоры:** FR-90, FR-92, FR-95, FR-96; AD-7, AD-18, AD-20, AD-35; кейс §3.3, §5.3; критерий Т2. Общие правила — [README.md](README.md).

**Все форматы и объекты Галактики в этом документе, кроме отмеченных «проверено по документации», — проектные предположения** (AD-18, NFR-DOC-2): публичной спецификации API Галактики нет, контракт — наш, по образцу реальных механизмов обмена.

## 1. Почему Галактика и какая

- Галактика реальна для отрасли: в июне 2026 года Роскосмос и «Корпорация Галактика» подписали меморандум о стратегическом партнёрстве до 2030 года — отраслевая система управления производством и межзаводской кооперацией на базе решений, опробованных в НПО «Энергомаш» (проверено по документации, открытые публикации). На предприятиях кооперации будут и 1С, и Галактика — поэтому архитектура «один порт учёта + адаптер на систему».
- Целевой продукт — **Галактика ERP 9.x** (платформа «Атлантис», язык VIP, трёхуровневая архитектура, PostgreSQL и Linux). Модули, касающиеся ОТК (проверено по документации «Галактика ERP. Основы использования»):
  - «Спецификации продуктов» — конструкторская и производственная спецификации, маршрутные карты;
  - «Управление производственной логистикой» — сменно-суточные задания, маршрутные листы, движение материалов между подразделениями;
  - «**Управление качеством продукции**» — ввод, хранение и обработка результатов контроля качества партий сырья, полуфабрикатов и готовой продукции; сертификаты качества.
- Значит, результат контроля в Галактике можно адресовать в объект качества, а не только в складской учёт.

## 2. Реальные механизмы обмена Галактики

Проверено по документации (актуальность для 9.x — оценка):

- **web-сервисы (SOAP/WSDL)**, генерируемые «Атлантисом» из опубликованных объектных интерфейсов; клиент работает с бизнес-объектами: запрашивает экземпляр, передаёт на сохранение, вызывает методы;
- **импорт и экспорт** в DBF, TXT (CSV), XML; таблицы обмена; репликация между разнесёнными базами; SQL-доступ через ODBC/ADO/JDBC;
- в развитии — **Галактика ESB** с API Manager (REST, gRPC, Kafka); по дорожной карте вендора MVP для ERP — рубеж 2025–2026, для MES — 2026–2027.

Из этого наш выбор (проектное предположение): **одна модель сообщения, два транспорта**.

1. **XML-пакет в каталоге или таблице обмена** — основной для 9.x; так же предприятия интегрируются через корпоративную шину. Квитанция — встречный XML с тем же `messageId`.
2. **REST-фасад «под Галактика ESB»** — на будущее, тот же пакет в JSON или XML по HTTP.

Транспорт выбирается конфигурацией канала (`transport: exchange-dir | rest-facade`), модель сообщения и порт учёта не меняются.

## 3. Направления, данные и шаги процесса

| Направление | Данные (порт учёта) | Объект Галактики (проектное предположение) | Шаг процесса |
|---|---|---|---|
| Галактика → «Главный» | справочник номенклатуры (каталог материальных ценностей) | каталог МЦ | до запуска |
| Галактика → «Главный» | производственное задание | сменно-суточное задание / маршрутный лист | запуск процесса изделий |
| Галактика → «Главный» | поступившая партия | приходная накладная + партия | ЗТ-1 входной контроль |
| «Главный» → Галактика | «принято в работу» | отметка в маршрутном листе | ЗТ-1 при выдаче в производство |
| «Главный» → Галактика | «смена склада» | накладная на внутреннее перемещение | ЗТ-2, ЗТ-3 |
| «Главный» → Галактика | «результат контроля» | запись результата контроля партии / экземпляра в «Управлении качеством продукции» | каждая подписанная ЗТ-1…ЗТ-6 и ЗТ-Р |
| «Главный» → Галактика | «перевод в брак» (переделка, списание, переработка) | запрос на доработку (сменное задание) / акт списания / акт пересортицы | ЗТ-Р |
| «Главный» → Галактика | «возврат поставщику» | накладная на возврат, основание претензии | ЗТ-Р по входному браку |
| «Главный» → Галактика | «выпуск» (`after_rework`, номер разрешения на отклонение) | сдача готовой продукции, сертификат качества | ЗТ-6 |
| Галактика → «Главный» | квитанция или ошибка (`GalAck`) | — | на каждое сообщение |

Закрывающие точки и правила «что никогда не уходит» — те же, что для 1С ([1c.md](1c.md), §3): сигналы, наблюдения, журналы станков, гипотезы, движение внутри цеха и блокировки в ERP не уходят.

## 4. Источник достоверных сведений

Как для 1С: номенклатура, задания, партии, остатки — Галактика; результаты контроля, решения по изделию, разрешения на отклонение, подписанные документы — «Главный». Если на предприятии работает и 1С, и Галактика, источник истины по каждому виду данных задаётся конфигурацией канала (обычно: бухгалтерский учёт — 1С, производственная логистика — Галактика), а «Главный» отправляет учётное действие в каждую включённую систему.

## 5. Сопоставление идентификаторов

- Суррогатный ключ записи Галактики — поле **`NRec`** (встречается в журнале изменений как идентификатор записи — по открытым материалам сообщества). Это 64-битное целое: в JSON оно теряет точность, поэтому **храним и передаём строкой**.
- Внешний ID в записи соответствия `reference.external_id.mapped`: `galaktika:‹база›:‹таблица›:‹NRec›`, например `galaktika:zavod2:KatMC:4611686018427388123`. Имена таблиц (`KatMC` — каталог МЦ, `KatSopr` / `SpSopr` — сопроводительные документы) — проектное предположение по примерам сообщества.
- В распределённой (филиальной) базе старшие разряды `NRec` могут кодировать филиал — поэтому в ключе есть база; проверить у вендора.
- Дополнительно храним код и номер документа (для людей). Правила конфликта и смены ID — общие ([README.md](README.md), §6.2).

## 6. Контракт `gal.qc.v1`

- Корневой элемент `GalExchange` в пространстве имён `urn:ant-qc:galaktika:v1`, атрибуты `messageId` (ключ идемпотентности, выведен из бизнес-ключа), `createdAt`, `from`, `to`, `contract`.
- Внутри — ровно одно сообщение порта учёта: исходящие `QualityLotResult` (результат контроля) и `Posting` (учётное действие, `kind`: `accept_to_work`, `internal_move`, `defect_rework`, `defect_writeoff`, `defect_reprocess`, `return_to_supplier`, `return_from_defect`, `release`), входящие `ProductionTask`, `LotReceived`, `ItemCatalog`. Бизнес-ключ и основание — вложенный `Source`.
- Квитанция — `GalAck` с `status="ok|error"`, `duplicate`, `code`, `text`, `nrecCreated`, `document`; описание ответной стороны — `GalAbout` (узел, база, поддерживаемые версии контракта).
- Значения перечислений в XML и JSON одинаковые, в нижнем регистре (`verdict="rejected"`, `status="ok"`); коды ошибок Галактики — прописными (`LOT_NOT_FOUND`).
- REST-фасад (проектное предположение): `POST /galaktika/esb/v1/quality/lot-results`, `POST /galaktika/esb/v1/production/postings` (JSON-форма пакета, заголовки `X-Message-Id`, `X-Contract-Version`), `GET /galaktika/esb/v1/exchange/outbox` (входящие пакеты), `GET /galaktika/esb/v1/about`.
- Каталог обмена: `out/‹номер›.xml` — пакеты Главного, `ack/‹номер›.xml` — квитанции Галактики, `in/*.xml` — пакеты Галактики, `in-ack/‹номер›.xml` — квитанции Главного, `about.xml` — версии контракта обработчика.
- Схемы — `contracts/integrations/erp/galaktika/gal.qc.v1.xsd` (XML, для обработчика на стороне Галактики) и `contracts/integrations/erp/galaktika/gal.qc.v1/*.schema.json` (JSON-форма; ею адаптер проверяет каждое исходящее сообщение до отправки на обоих транспортах); эталонные сообщения — `contracts/integrations/erp/galaktika/examples/`; словарь имён XML ↔ JSON — `contracts/integrations/erp/galaktika/README.md`.
- Какие поля реально нужны модулю «Управление качеством продукции» (показатели, нормативный документ, номер удостоверения качества) — не проверено; уточнить у вендора.

## 7. Примеры сообщений

Полный набор — `contracts/integrations/erp/galaktika/examples/` (контрактный тест сверяет с ним вывод адаптера).

**1. Входящее сменное задание (каталог обмена → Главный):**

```xml
<GalExchange xmlns="urn:ant-qc:galaktika:v1" messageId="GAL-2026-09-25-000117" createdAt="2026-09-25T05:00:00.000Z" from="GAL-ERP-ZAVOD2" to="ant" contract="gal.qc.v1">
  <ProductionTask nrec="4611686018427399001" table="MnPlan" number="СЗ-000812" date="2026-09-25" dueDate="2026-10-02" quantity="6" routeSheet="МЛ-000812" kdRevision="Б">
    <Item designation="ФЛ-100.00.000 СБ" name="Фланец люка гермокорпуса в сборе" nrec="4611686018427388123" table="KatMC"></Item>
  </ProductionTask>
</GalExchange>
```

Главный получает из него `erp.order.received` (задание `ORD-SZ-000812`, тип изделия `FL-100.00.000`, 6 шт., версия КД «Б») и соответствия `galaktika:zavod2:MnPlan:4611686018427399001 → ORD-SZ-000812`, `galaktika:zavod2:KatMC:4611686018427388123 → FL-100.00.000`.

**2. Исходящий результат контроля партии (Главный → «Управление качеством продукции»):**

```xml
<GalExchange xmlns="urn:ant-qc:galaktika:v1" messageId="bc706d05-d7d6-5cde-9c48-ede1e6b80488" createdAt="2026-09-25T10:42:17.305Z" from="ant" to="GAL-ERP-ZAVOD2" contract="gal.qc.v1">
  <QualityLotResult presentation="1" verdict="rejected">
    <Source businessKey="LOT-B-0915/inspection_result/ZT-1" messageVersion="1" enterprise="ENT01" closingPoint="ZT-1"></Source>
    <Lot lotId="LOT-B-0915" quantity="12"></Lot>
    <ProductionOrder orderId="ORD-0812"></ProductionOrder>
    <Nonconformity ref="NC-2026-0031"></Nonconformity>
    <Nonconformity ref="NC-2026-0032"></Nonconformity>
  </QualityLotResult>
</GalExchange>
```

**3. Квитанция:**

```xml
<GalAck xmlns="urn:ant-qc:galaktika:v1" messageId="3c6f1d0e-8a1b-5c9e-9f0a-1b2c3d4e5f60" status="ok" nrecCreated="4611686018427400555" document="АКТК-000077" receivedAt="2026-09-25T10:42:18.120Z"></GalAck>
```

**4. Ошибка:**

```xml
<GalAck xmlns="urn:ant-qc:galaktika:v1" messageId="3c6f1d0e-8a1b-5c9e-9f0a-1b2c3d4e5f60" status="error" code="LOT_NOT_FOUND" text="Партия П-2026-0915 не найдена в каталоге партий"></GalAck>
```

## 8. Подтверждения и обработка ошибок

| Ответ | Поведение «Главного» |
|---|---|
| `GalAck status="OK"` | квитанция → событие журнала, ось учёта меняется |
| повтор того же `messageId` | Галактика (или фасад) возвращает прежнюю квитанцию; двойного учёта нет |
| `GalAck status="ERROR"` с бизнес-кодом (`LOT_NOT_FOUND`, `ITEM_NOT_MAPPED` …) | без автоповтора → карантин исходящих, задача администратору, ручная переотправка с тем же `messageId` |
| нет квитанции за время ожидания (файловый канал) | повтор с тем же `messageId` по расписанию повторов, затем карантин |
| транспорт REST-фасада: `5xx`, таймаут | автоповтор с экспоненциальной задержкой, затем карантин |
| `401` / `403` | канал на паузу, тревога |
| пакет не проходит XSD или неизвестная версия контракта в квитанции | канал `degraded`, отправка остановлена (AD-18) |

Входящий пакет из каталога обмена проходит обычный приём: XSD, идемпотентность по `messageId` источника, карантин с кодом при ошибке; квитанция `GalAck` на входящий пакет пишется в каталог обмена только после записи факта в журнал.

## 9. Граница эмуляции (NFR-TEST-2)

- **Stand Галактики (эпик 43)** — за тем же контрактом `gal.qc.v1`, на обоих транспортах: обрабатывает каталог обмена (объявляет `about.xml`, забирает пакеты из `out/`, кладёт квитанции `GalAck` в `ack/`, свои пакеты — в `in/`, читает квитанции «Главного» из `in-ack/`) и отвечает REST-фасадом `/stand/galaktika/esb/v1/`. По каждому принятому пакету — документ Галактики (акт контроля качества, требование-накладная, накладная на перемещение, акт о браке, возвратная накладная, сдача продукции), сторно при исправлении; повтор номера — та же квитанция (`duplicate`), второго документа нет.
- Сбои — только с пульта тестовых сценариев через служебный порт stand-ов (AD-18): `offline` (каталог не обрабатывается, фасад рвёт соединение), `error` (`param` 422 — квитанция с ошибкой данных, код по тексту: «договор» → `CONTRACT_NOT_FOUND`, «партия» → `LOT_NOT_FOUND`, «склад» → `WAREHOUSE_NOT_FOUND`, иначе `DATA_ERROR`; 5xx — квитанции нет, повтор; `match` — только пакет по образцу `вид:субъект`, например `release:F-001`), `delay` (мс), `duplicate` (ответ фасада потерян), `corrupt` (обработчик объявляет только `gal.qc.v2` — канал `degraded`).
- Stand не имитирует прикладную логику Галактики (учёт МЦ, проводки, себестоимость, VIP-интерфейс «Атлантиса», права) — только приём, квитанции, документы «что получено», задания и партии по кнопкам и сбои. Состояние — в памяти роли `stands`; квитанции каталога лежат в томе и переживают перезапуск.

**Где в коде:** `backend/internal/infrastructure/integration/erp/galaktika/` (клиент), `…/erp/galaktika/stand/` (stand, эпик 43).

## 10. Путь к реальной Галактике

1. Согласовать с вендором или интегратором состав полей модуля «Управление качеством продукции» и формат `NRec` в филиальной базе; дополнить схему `gal.qc.v1`.
2. На стороне Галактики — обработчик каталога или таблицы обмена на VIP (или опубликованный объектный интерфейс — web-сервис «Атлантиса»), принимающий `GalExchange` и отвечающий `GalAck`.
3. После появления REST в Галактика ESB — переключить транспорт на `rest-facade` конфигурацией.
4. Порт учёта, домен и контракт событий «Главного» не меняются.

## В коде (эпик 31)

- **Адаптер:** `backend/internal/infrastructure/integration/erp/galaktika` — реализация порта учёта `application/erp.Ledger` на двух транспортах (`exchange-dir`, `rest-facade`); ядро, домен `erp` и роль `outbox` не менялись. Как подключить — [new-adapter.md](../new-adapter.md).
- **Контрактные тесты:** `go test ./internal/infrastructure/integration/erp/...` — эталоны по схемам и XSD, внутренний сигнал порта → эталонные пакеты, общий тест порта учёта `application/erp/ledgertest` на обоих транспортах Галактики и на stand-е 1С, классы ответа, входящие факты.
- **Коды ошибок `GalAck` → `contracts/errors.yaml`:** `LOT_NOT_FOUND`, `ITEM_NOT_MAPPED`, `ITEM_NOT_FOUND`, `WAREHOUSE_NOT_FOUND`, `ORDER_NOT_FOUND` → `erp.id_mapping_missing`; `CONTRACT_NOT_FOUND` → `erp.contract_not_found`; прочие → `erp.data_error`; `CONTRACT_VERSION`, `SCHEMA_VIOLATION` — несовместимость (канал `degraded`).
- **Внешние ID:** `galaktika:‹база›:‹таблица›:‹NRec›`; наши ID: задание `ORD-‹номер латиницей›`, партия `LOT-‹номер партии›`, поставщик — код латиницей, тип изделия — обозначение КД по правилу `domain/cad.ItemTypeID` (то же, что у 1С и КОМПАС). Источник входящих — `erp.galaktika`.
- **Конфигурация:** ключи `erp.galaktika.*` (транспорт, каталог, адрес фасада, узлы, база, таймауты, повторы) и фабрика порта в `cmd/ant` — [new-adapter.md](../new-adapter.md), шаги 4–5. В MVP порт учёта обслуживает одну учётную систему на экземпляр (`integrations.enabled`); одновременная отправка в 1С и Галактику требует ключа сообщения с системой — описано там же, §5.
- **Stand Галактики** — эпик 43, раздел ниже.

## Как поднять stand Галактики (эпик 43)

«Главный» в профиле `demo` уже поднимает stand: `docker compose up` (или `make demo`) — в `deploy/config/ant.yaml` у профиля `demo` `integrations.enabled` содержит `galaktika`, `erp.galaktika.stand: true`, транспорт `exchange-dir`, каталог `/var/lib/ant/exchange/galaktika` — том `exchange` в `deploy/compose/compose.yaml` (корень ФС контейнера только для чтения; адаптер роли `outbox` и stand роли `stands` пишут в этот том).

1. **Экран «Интеграции»** стола администратора: Галактика — «установлена», режим «стенд». «Проверить соединение» — та же сверка, что при старте адаптера: `about.xml` из каталога обмена, версия `gal.qc.v1` (ответ `ok`, адрес `file:///var/lib/ant/exchange/galaktika`).
2. **Учётный обмен** в `demo` ведёт 1С (`erp.ledger: onec`: одна учётная система на экземпляр). Переключить на Галактику — перезапуск с переменной:
   ```sh
   ANT_ERP_LEDGER=galaktika docker compose up -d
   ```
   Роль `projector` начинает формировать учётные сообщения для Галактики, роль `outbox` — класть пакеты в `out/` и забирать квитанции из `ack/`; stand обходит каталог раз в секунду. Вернуть 1С — `ANT_ERP_LEDGER=onec` (или без переменной).
3. **Страница stand-а** — `http://127.0.0.1:${ANT_STANDS_PORT:-8491}/stand/galaktika/`: описание обработчика, кнопки «Выдать задание» (пакет `ProductionTask` → `erp.order.received`) и «Оприходовать» партию (`LotReceived` → `erp.lot.received`), квитанции «Главного» на них, журнал обмена (номер пакета, квитанция, число доставок, сбои) и документы Галактики.
4. **Состояние для проверок** — `GET /stand/galaktika/state` (JSON); сбои — `POST /stand/_control/galaktika/faults` `{"kind":"error","param":422,"match":"release:F-001","detail":"Договор не найден"}` с пульта сценариев, снять — `DELETE /stand/_control/galaktika/faults`.
5. **REST-фасад** вместо каталога: `erp.galaktika.transport: rest-facade` и пустой `base_url` со `stand: true` — адаптер идёт в `/stand/galaktika/esb/v1` своего хоста.

Проверка без стека: `go test ./internal/infrastructure/integration/erp/galaktika/...` — общий контрактный тест порта учёта (`application/erp/ledgertest`) на stand-е по обоим транспортам, сбои stand-а, кнопки страницы.
