# Интеграция с Галактика ERP

Двусторонний обмен с Галактика ERP через отдельный адаптер без изменения ядра (FR-92, кейс §3.3). В MVP — адаптер в коде, контракт `gal.qc.v1`, эталонные сообщения и контрактный тест; stand Галактики — в очереди работ. Тот же внутренний сигнал порта учёта, что уходит в 1С, может уйти и в Галактику — какие системы включены, задаёт конфигурация.

**Опоры:** FR-90, FR-92, FR-95, FR-96; AD-7, AD-18, AD-20, AD-35; кейс §3.3, §5.3; критерий Т2. Общие правила — [README.md](README.md).

**Все форматы и объекты Галактики в этом документе, кроме отмеченных «проверено по документации», — проектные предположения** (AD-18, NFR-DOC-2): публичной спецификации API Галактики нет, контракт — наш, по образцу реальных механизмов обмена.

## 1. Почему Галактика и какая

- Галактика реальна для отрасли: в июне 2026 года Роскосмос и «Корпорация Галактика» подписали меморандум о стратегическом партнёрстве до 2030 года — отраслевая система управления производством и межзаводской кооперацией на базе решений, опробованных в НПО «Энергомаш» (проверено по документации, открытые публикации). На предприятиях кооперации будут и 1С, и Галактика — поэтому архитектура «один порт учёта + адаптер на систему».
- Целевой продукт — **Галактика ERP 9.x** (платформа «Атлантис», язык VIP, трёхуровневая архитектура, PostgreSQL и Linux). Модули, касающиеся ОТК (проверено по документации «Галактика ERP. Основы использования»):
  - «Спецификации продуктов» — конструкторская и производственная спецификации, маршрутные карты;
  - «Управление производственной логистикой» — сменно-суточные задания, маршрутные листы, движение материалов между подразделениями;
  - «**Управление качеством продукции**» — ввод, хранение и обработка результатов контроля качества партий сырья, полуфабрикатов и готовой продукции; сертификаты качества.
- Значит, результат контроля в Галактике можно адресовать в объект качества, а не только в складской учёт.

## 2. Реальные механизмы обмена Галактики

Проверено по документации (актуальность для 9.x — оценка):

- **web-сервисы (SOAP/WSDL)**, генерируемые «Атлантисом» из опубликованных объектных интерфейсов; клиент работает с бизнес-объектами: запрашивает экземпляр, передаёт на сохранение, вызывает методы;
- **импорт и экспорт** в DBF, TXT (CSV), XML; таблицы обмена; репликация между разнесёнными базами; SQL-доступ через ODBC/ADO/JDBC;
- в развитии — **Галактика ESB** с API Manager (REST, gRPC, Kafka); по дорожной карте вендора MVP для ERP — рубеж 2025–2026, для MES — 2026–2027.

Из этого наш выбор (проектное предположение): **одна модель сообщения, два транспорта**.

1. **XML-пакет в каталоге или таблице обмена** — основной для 9.x; так же предприятия интегрируются через корпоративную шину. Квитанция — встречный XML с тем же `messageId`.
2. **REST-фасад «под Галактика ESB»** — на будущее, тот же пакет в JSON или XML по HTTP.

Транспорт выбирается конфигурацией канала (`transport: exchange-dir | rest-facade`), модель сообщения и порт учёта не меняются.

## 3. Направления, данные и шаги процесса

| Направление | Данные (порт учёта) | Объект Галактики (проектное предположение) | Шаг процесса |
|---|---|---|---|
| Галактика → `ant` | справочник номенклатуры (каталог материальных ценностей) | каталог МЦ | до запуска |
| Галактика → `ant` | производственное задание | сменно-суточное задание / маршрутный лист | запуск процесса изделий |
| Галактика → `ant` | поступившая партия | приходная накладная + партия | ЗТ-1 входной контроль |
| `ant` → Галактика | «принято в работу» | отметка в маршрутном листе | ЗТ-1 при выдаче в производство |
| `ant` → Галактика | «смена склада» | накладная на внутреннее перемещение | ЗТ-2, ЗТ-3 |
| `ant` → Галактика | «результат контроля» | запись результата контроля партии / экземпляра в «Управлении качеством продукции» | каждая подписанная ЗТ-1…ЗТ-6 и ЗТ-Р |
| `ant` → Галактика | «перевод в брак» (переделка, списание, переработка) | запрос на доработку (сменное задание) / акт списания / акт пересортицы | ЗТ-Р |
| `ant` → Галактика | «возврат поставщику» | накладная на возврат, основание претензии | ЗТ-Р по входному браку |
| `ant` → Галактика | «выпуск» (`after_rework`, номер разрешения на отклонение) | сдача готовой продукции, сертификат качества | ЗТ-6 |
| Галактика → `ant` | квитанция или ошибка (`GalAck`) | — | на каждое сообщение |

Закрывающие точки и правила «что никогда не уходит» — те же, что для 1С ([1c.md](1c.md), §3): сигналы, наблюдения, журналы станков, гипотезы, движение внутри цеха и блокировки в ERP не уходят.

## 4. Источник достоверных сведений

Как для 1С: номенклатура, задания, партии, остатки — Галактика; результаты контроля, решения по изделию, разрешения на отклонение, подписанные документы — `ant`. Если на предприятии работает и 1С, и Галактика, источник истины по каждому виду данных задаётся конфигурацией канала (обычно: бухгалтерский учёт — 1С, производственная логистика — Галактика), а `ant` отправляет учётное действие в каждую включённую систему.

## 5. Сопоставление идентификаторов

- Суррогатный ключ записи Галактики — поле **`NRec`** (встречается в журнале изменений как идентификатор записи — по открытым материалам сообщества). Это 64-битное целое: в JSON оно теряет точность, поэтому **храним и передаём строкой**.
- Внешний ID в записи соответствия `reference.external_id.mapped`: `galaktika:‹база›:‹таблица›:‹NRec›`, например `galaktika:zavod2:KatMC:4611686018427388123`. Имена таблиц (`KatMC` — каталог МЦ, `KatSopr` / `SpSopr` — сопроводительные документы) — проектное предположение по примерам сообщества.
- В распределённой (филиальной) базе старшие разряды `NRec` могут кодировать филиал — поэтому в ключе есть база; проверить у вендора.
- Дополнительно храним код и номер документа (для людей). Правила конфликта и смены ID — общие ([README.md](README.md), §6.2).

## 6. Контракт `gal.qc.v1`

- Корневой элемент `GalExchange` в пространстве имён `urn:ant-qc:galaktika:v1`, атрибуты `messageId` (ключ идемпотентности, выведен из бизнес-ключа), `createdAt`, `from`, `to`, `contract`.
- Внутри — одно сообщение порта учёта: `QualityLotResult` (результат контроля), `Posting` (учётное действие), входящие `ProductionTask`, `LotReceived`, `ItemCatalog`.
- Квитанция — `GalAck` с `status="OK|ERROR"`, `code`, `text`, `nrecCreated`.
- REST-фасад (проектное предположение): `POST /galaktika/esb/v1/quality/lot-results`, `POST /galaktika/esb/v1/production/postings`, `GET /galaktika/esb/v1/nsi/items?changedSince=…`.
- Схема — `contracts/integrations/erp/galaktika/gal.qc.v1.xsd`; эталонные сообщения — `contracts/integrations/erp/galaktika/examples/` (пути предварительные).
- Какие поля реально нужны модулю «Управление качеством продукции» (показатели, нормативный документ, номер удостоверения качества) — не проверено; в схеме отмечены как «уточнить у вендора».

## 7. Примеры сообщений

**1. Входящее сменное задание (каталог обмена → `ant`):**

```xml
<GalExchange xmlns="urn:ant-qc:galaktika:v1" messageId="GAL-2026-09-25-000117"
             createdAt="2026-09-25T05:00:00.000Z" from="GAL-ERP-ZAVOD2" to="ant" contract="gal.qc.v1">
  <ProductionTask nrec="4611686018427399001" table="MnPlan" number="СЗ-000812" date="2026-09-25">
    <Item nrec="4611686018427388123" table="KatMC" designation="ФЛ-100.00.000" name="Фланец люка в сборе"/>
    <Quantity value="6" unit="шт"/>
    <RouteSheet number="МЛ-000812"/>
    <KdRevision value="Б"/>
  </ProductionTask>
</GalExchange>
```

**2. Исходящий результат контроля партии (`ant` → «Управление качеством продукции»):**

```xml
<GalExchange xmlns="urn:ant-qc:galaktika:v1" messageId="b3d1f0a2-5c6e-5a7b-9c8d-0e1f2a3b4c5d"
             createdAt="2026-09-25T10:42:17.305Z" from="ant" to="GAL-ERP-ZAVOD2" contract="gal.qc.v1">
  <QualityLotResult closingPoint="ЗТ-1" presentation="1">
    <Item nrec="4611686018427388124" table="KatMC" designation="ФЛ-100.00.010" itemId="ENT01:LOT-B-0915"/>
    <Lot number="П-2026-0915" serials="0411-0422"/>
    <ProductionOrder nrec="4611686018427399001" routeSheet="МЛ-000812"/>
    <Result verdict="REJECTED" accepted="10" rejected="2" nonconformities="НС-2026-0031 НС-2026-0032"/>
    <Disposition kind="RETURN_TO_SUPPLIER" decisionDoc="РШ-2026-0077" digest="streebog256:4c2e…"/>
    <SignedBy person="К-0042" role="контролёр качества" at="2026-09-25T10:41:58.004Z"/>
  </QualityLotResult>
</GalExchange>
```

**3. Квитанция:**

```xml
<GalAck xmlns="urn:ant-qc:galaktika:v1" messageId="b3d1f0a2-5c6e-5a7b-9c8d-0e1f2a3b4c5d" status="OK" nrecCreated="4611686018427400555"/>
```

**4. Ошибка:**

```xml
<GalAck xmlns="urn:ant-qc:galaktika:v1" messageId="b3d1f0a2-5c6e-5a7b-9c8d-0e1f2a3b4c5d" status="ERROR"
        code="LOT_NOT_FOUND" text="Партия П-2026-0915 не найдена в каталоге партий"/>
```

## 8. Подтверждения и обработка ошибок

| Ответ | Поведение `ant` |
|---|---|
| `GalAck status="OK"` | квитанция → событие журнала, ось учёта меняется |
| повтор того же `messageId` | Галактика (или фасад) возвращает прежнюю квитанцию; двойного учёта нет |
| `GalAck status="ERROR"` с бизнес-кодом (`LOT_NOT_FOUND`, `ITEM_NOT_MAPPED` …) | без автоповтора → карантин исходящих, задача администратору, ручная переотправка с тем же `messageId` |
| нет квитанции за время ожидания (файловый канал) | повтор с тем же `messageId` по расписанию повторов, затем карантин |
| транспорт REST-фасада: `5xx`, таймаут | автоповтор с экспоненциальной задержкой, затем карантин |
| `401` / `403` | канал на паузу, тревога |
| пакет не проходит XSD или неизвестная версия контракта в квитанции | канал `degraded`, отправка остановлена (AD-18) |

Входящий пакет из каталога обмена проходит обычный приём: XSD, идемпотентность по `messageId` источника, карантин с кодом при ошибке; квитанция `GalAck` на входящий пакет пишется в каталог обмена только после записи факта в журнал.

## 9. Граница эмуляции (NFR-TEST-2)

- **В MVP stand-а нет.** Есть адаптер (клиент), схема, эталонные сообщения и контрактный тест: адаптер формирует пакет из сообщения порта учёта, пакет валидируется XSD и сравнивается с эталоном; разбор эталонной квитанции и эталонной ошибки даёт ожидаемые события.
- **В очереди** — stand за тем же протоколом: файловый приёмник (каталог обмена со своим состоянием в схеме `stand_galaktika`) и REST-фасад, квитанции и сбои (ошибка, дубль, недоступность), как у stand-а 1С.
- Stand не имитирует прикладную логику Галактики (учёт МЦ, себестоимость, сертификаты качества) — только приём, квитанции, состояние «что получено» и сбои.

**Где в коде:** `backend/internal/infrastructure/integration/erp/galaktika/` (клиент), `…/erp/galaktika/stand/` (stand, очередь).

## 10. Путь к реальной Галактике

1. Согласовать с вендором или интегратором состав полей модуля «Управление качеством продукции» и формат `NRec` в филиальной базе; дополнить схему `gal.qc.v1`.
2. На стороне Галактики — обработчик каталога или таблицы обмена на VIP (или опубликованный объектный интерфейс — web-сервис «Атлантиса»), принимающий `GalExchange` и отвечающий `GalAck`.
3. После появления REST в Галактика ESB — переключить транспорт на `rest-facade` конфигурацией.
4. Порт учёта, домен и контракт событий `ant` не меняются.
