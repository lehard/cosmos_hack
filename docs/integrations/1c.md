# Интеграция с 1С:ERP

Живой двусторонний обмен MVP (кейс §3.3, §1.5, FR-91): из 1С в «Главный» приходят номенклатура, производственные задания и поступившие партии; из «Главного» в 1С на закрывающих точках уходят учётные последствия решений и результат контроля; на каждое сообщение 1С отвечает квитанцией или ошибкой. В демо на месте 1С работает stand — эмулятор за тем же протоколом.

**Опоры:** FR-90, FR-91, FR-95, FR-96, FR-130; AD-7, AD-18, AD-20, AD-30; кейс §1.5, §3.3, §5.3; критерии Т2, О8. Общие правила — [README.md](README.md).

Пометки достоверности: **проверено по документации** — подтверждено открытыми материалами 1С и интеграторов (собраны в исследовании интеграций этапа планирования); **проектное предположение** — наше решение или оценка, требует проверки на реальной базе 1С предприятия (NFR-DOC-2).

## 1. Какая 1С и почему именно она

- Целевая конфигурация — **1С:ERP Управление предприятием 2.5** и **1С:ERP Управление холдингом** (контур «Управление производством 2.2»: заказ на производство + этапы производства). По открытым материалам отраслевых внедрений именно ERP УХ стоит в учётном контуре предприятий ракетно-космической отрасли, а учёт брака там автоматизирован в 1С (проверено по документации).
- 1С:Комплексная автоматизация 2.5 — тот же контракт, часть объектов может отсутствовать; это ловит сверка `$metadata` (§8). 1С:УПП 1.3 — только как профиль сопоставления, без эмуляции.
- Живой stand сделан для 1С, а не для MES или Галактики: 1С прямо требует кейс, у неё публичный и проверяемый интерфейс (OData, коды ошибок), а у MES и Галактики публичной спецификации нет.

## 2. Направления и данные

| Направление | Данные (порт учёта, наш язык) | Документ / объект 1С | Протокол | Достоверность |
|---|---|---|---|---|
| 1С → «Главный» | справочник номенклатуры | справочник «Номенклатура» (+ виды, характеристики) — `Catalog_Номенклатура` | OData, чтение | проверено по документации (объект) |
| 1С → «Главный» | серии (партии) номенклатуры | справочник «Серии номенклатуры» — `Catalog_СерииНоменклатуры` | OData, чтение | механизм проверен; имя ресурса — проектное предположение |
| 1С → «Главный» | производственное задание | «Заказ на производство» — `Document_ЗаказНаПроизводство2_2`; «Этап производства» — `Document_ЭтапПроизводства2_2` | OData, чтение | проверено по документации |
| 1С → «Главный» | поступившая партия | «Приобретение товаров и услуг» / приходный документ + серия | OData, чтение | проектное предположение |
| 1С → «Главный» | подразделения, склады, рабочие центры | `Catalog_СтруктураПредприятия`, `Catalog_Склады`, `Catalog_РабочиеЦентры` | OData, чтение | объекты проверены; имена ресурсов — проектное предположение |
| «Главный» → 1С | учётные действия на закрывающих точках (§3) | см. таблицу §3 | HTTP-сервис расширения `/hs/qc/v1/` | проектное предположение (наша спецификация расширения) |
| «Главный» → 1С | результат контроля | отметка результата контроля на этапе / серии со ссылкой на подписанный документ «Главного» | HTTP-сервис расширения | проектное предположение |
| 1С → «Главный» | квитанция или ошибка | ответ HTTP-сервиса; `odata.error` | HTTP | см. §6 |

**Почему читаем через OData, а пишем через HTTP-сервис.** У стандартного интерфейса OData нет пакетов (`$batch`) и идемпотентности, а документ ERP, созданный через OData, не проходит прикладную логику заполнения. Поэтому в реальных проектах читают через OData, а пишут через HTTP-сервис расширения конфигурации, который принимает агрегат целиком, заполняет документы по правилам ERP в одной транзакции и хранит ключ идемпотентности (проверено по документации; наш сервис `qc` — проектное предположение). Так же закреплено в AD-18.

**Чего в 1С нет.** В типовой 1С:ERP нет объектов «несоответствие» и «разрешение на отклонение»; качество выражено градациями «Новый / Ограниченно годен / Не годен» и документами-последствиями («Этап производства», «Порча товаров», «Пересортица товаров», «Внутреннее потребление товаров», «Возврат товаров поставщику», «Акт о расхождениях после поступления») (проверено по документации). Поэтому карточка несоответствия, решения и подписанные документы остаются в «Главном», а в 1С уходят только учётные последствия и ссылка на наш документ.

## 3. Шаги процесса: закрывающие точки и что уходит в 1С

Маршрут демо-изделия (фланец люка ФЛ-100): входной контроль → мехобработка → сварка → сборка → испытание на герметичность → окончательный контроль ОТК. Цеха — механический, сварочный, сборочно-испытательный, у каждого свой склад (FR-130; число цехов — проектное предположение процессной части). На закрывающей точке изделие стоит, пока уполномоченный человек не подпишет решение; учётное действие — реакция движка на подписанное решение.

| ЗТ | Где | Что уходит в 1С (порт учёта) | Объект 1С:ERP (проектное предположение) |
|---|---|---|---|
| — | получено задание из 1С | ничего не отправляем; задание запускает процесс изделий (стартовое событие BPMN по сообщению, решение Д-5) | чтение «Этапа производства» |
| ЗТ-1 | входной контроль: партия, заготовка, покупные детали | годное — **«принято в работу»** в момент выдачи в производство (заготовка — при запуске, крышка и крепёж — при выдаче на сборку); брак партии — через ЗТ-Р **«возврат поставщику»** | отметка начала «Этапа производства» / передача материалов в производство |
| ЗТ-2 | после мехобработки | **«смена склада»**: механический цех → сварочный; уходит, когда цех-получатель принял изделие | «Перемещение товаров» между складами цехов |
| ЗТ-3 | после сварки | **«смена склада»**: сварочный цех → сборочно-испытательный; повторная ЗТ-3 после удачной переделки шва — сначала **«возврат из брака в производство»** (предварительно) | «Перемещение товаров»; возврат из брака — смена качества «Не годен» → «Новый» («Пересортица» / «Этап производства») |
| ЗТ-4 | после сборки | ничего (внутри цеха) | — |
| ЗТ-5 | испытание на герметичность | ничего (внутри цеха) | — |
| ЗТ-6 | окончательный контроль ОТК | **«выпуск»** — только здесь; изделие, принятое после переделки, — с признаком `after_rework`; «годно по разрешению на отклонение» — выпуск **с номером разрешения на отклонение** | выпуск продукции по «Этапу производства» / «Передача продукции из производства»; номер разрешения — дополнительным сведением серии и присоединённым файлом |
| ЗТ-Р | решение по несоответствию, на любом шаге | переделка, ремонт → **«перевод в брак (переделка)»**; списать → **«перевод в брак (списание)»**; разобрать сборку → **«перевод в брак (переработка)»**; вернуть поставщику → **«возврат поставщику»** с основанием претензии; «как есть» → сейчас ничего, позже «выпуск» с номером разрешения; повторное решение о ремонте, пока изделие в браке, нового движения не даёт | «Этап производства»: разбить строку → изменить качество; списание — «Внутреннее потребление товаров»; возврат — «Акт о расхождениях после поступления» → «Возврат товаров поставщику» |
| ЗТ-В | закрытие вскрытия собранного изделия | ничего | — |
| каждая подписанная ЗТ-1…ЗТ-6 и ЗТ-Р | — | **«результат контроля»** — одно сообщение на подписанное решение: закрывающая точка и номер предъявления, изделие или партия, задание, номенклатура, итог (годно / годно по разрешению на отклонение № … / не годно), при «не годно» — номера несоответствий, кратко дефекты и решение, кто и когда подписал, наши ID. Изделие не держит; движения не означает | в типовой ERP отдельного объекта нет — отметка результата контроля на этапе / серии в расширении `qc` (ближайшие аналоги — «акт контроля качества» отраслевых расширений) |

**Никогда не уходят в 1С:** сигналы и признаки дефекта, наблюдения камер, снимки, журналы станков, гипотезы причин, решения контролёра по сигналам (подтвердить / отклонить сигнал), движения внутри цеха, изоляция, **блокировки** (AD-18; блок уходит только в MES). При воспроизведении истории в 1С ничего не отправляется.

**Изолятор** — место в цехе, а не склад 1С (проектное предположение процессной части): в 1С уходит только итоговое решение. Если на предприятии изолятор — отдельный склад, изоляция станет учётным действием «смена склада» — это меняет только доменное правило модуля `erp` и конфигурацию, а не адаптер.

**«Возврат из брака в производство»** предложен процессной частью и в перечень порта учёта спайна (AD-18) пока не входит — включение фиксирует контракт (эпики 00, 30). До этого: удачная переделка отражается в 1С признаком `after_rework` при выпуске.

## 4. Источник достоверных сведений

| Данные | Источник истины | Что делает «Главный» |
|---|---|---|
| Номенклатура, склады, подразделения, рабочие центры | 1С | читает, хранит соответствие ID; номенклатуру в 1С не создаёт |
| Заказы и этапы производства, наряд-заказ / направление деятельности (раздельный учёт по контракту) | 1С | читает; аналитику наряд-заказа переносит в каждое исходящее сообщение |
| Серии закупленных партий | 1С | входной контроль ссылается на серию 1С |
| Заводской номер изготовленного экземпляра | «Главный» при регистрации изделия (проектное предположение) | регистрирует серию в 1С при выпуске |
| Результат контроля, решение по изделию, разрешение на отклонение, подписанные документы | «Главный» | в 1С — только учётное последствие и ссылка на документ с отпечатком |
| Остатки, себестоимость, списания, возвраты | 1С | «Главный» не ведёт |

## 5. Сопоставление идентификаторов

- Внешний ID объекта 1С — `Ref_Key` (GUID). Дополнительно храним `Code` / `Number` + `Date` (для людей и отчётов) и `DataVersion` (для перечитывания). `Code` и `Number` не уникальны во времени (префиксы, периодичность нумерации) — ключом не служат. Нулевой GUID `00000000-0000-0000-0000-000000000000` — пустая ссылка. `DeletionMark=true` — пометка удаления, а не удаление (проверено по документации).
- Каждое соответствие — запись `reference.external_id.mapped` с системой `1c-erp`, экземпляром базы (например, `erp-prod`), типом объекта (`Catalog_Номенклатура`, `Document_ЭтапПроизводства2_2` …), `Ref_Key`, `DataVersion` и нашим ID. Изменился `DataVersion` задания — адаптер перечитывает задание (его могли перепланировать) и подаёт новый факт.
- Изделие получает наш ID `код_предприятия:локальный_id`; из `Ref_Key` он не выводится (AD-16).
- В исходящем сообщении — и `Ref_Key` объектов 1С (этап, номенклатура, серия), и наш ID, и естественный ключ (обозначение по ЕСКД, заводской номер).
- Сопоставление с КОМПАС-3D — по обозначению детали (+ исполнение), см. [kompas.md](kompas.md), §5.

## 6. Контракт

### 6.1 Чтение: стандартный интерфейс OData v3

Базовый адрес — `http(s)://‹хост›/‹база›/odata/standard.odata/`; метаданные — `$metadata`; ответы JSON (`$format=json`); аутентификация — HTTP Basic пользователем с правом удалённого доступа OData (проверено по документации). Адаптер опрашивает 1С с интервалом из конфигурации:

```text
GET /erp/odata/standard.odata/$metadata
GET /erp/odata/standard.odata/Catalog_Номенклатура?$format=json&$select=Ref_Key,DataVersion,Code,Description,Артикул,НаименованиеПолное,DeletionMark
GET /erp/odata/standard.odata/Document_ЭтапПроизводства2_2?$format=json&$filter=Posted eq true and Статус eq 'КВыполнению'&$orderby=Date
GET /erp/odata/standard.odata/Document_ЭтапПроизводства2_2(guid'3f1c2a54-7b8e-11f0-9c1d-00155d0a1b2c')?$format=json
```

Инкрементальная выгрузка через план обмена (`SelectChanges` / `NotifyChangesReceived`) — вариант для реальной 1С; подтверждение `NotifyChangesReceived` отдаётся только после записи фактов в журнал «Главного».

Имена реквизитов и табличных частей (`Статус`, `ВыходныеИзделия`, `Распоряжение_Key` …) — **проектное предположение**, сверяются с `$metadata` реальной базы; ожидаемый набор зафиксирован в манифесте (§8).

### 6.2 Запись: HTTP-сервис расширения `qc`, версия `qc.v1`

Расширение конфигурации «КонтрольКачества» публикует корень `qc` (наша спецификация, проектное предположение). Типовая конфигурация не меняется.

| Метод и путь | Назначение |
|---|---|
| `POST /‹база›/hs/qc/v1/postings` | учётное действие порта учёта: `accepted_to_work`, `warehouse_transfer`, `moved_to_defect` (вид: `rework` / `scrap` / `reprocessing`), `returned_to_supplier`, `released`, предварительно `returned_from_defect` |
| `POST /‹база›/hs/qc/v1/inspection-results` | результат контроля по подписанной закрывающей точке |
| `GET /‹база›/hs/qc/v1/messages/{messageId}` | статус обработки сообщения (повторно выдаёт квитанцию) |

Заголовки: `Authorization: Basic …`, `Content-Type: application/json`, `X-Message-Id: ‹UUID›` — ключ идемпотентности, детерминированно выведенный из бизнес-ключа (субъект, учётное действие, закрывающая точка), `X-Contract-Version: qc.v1`.

Схемы тел — `contracts/integrations/erp/1c/qc.v1/*.schema.json`; манифест ожидаемых метаданных OData — `contracts/integrations/erp/1c/metadata-manifest.yaml`; эталонные сообщения — `contracts/integrations/erp/1c/examples/` (пути предварительные).

**3. Квитанция и повтор:**

```json
{"message_id": "6f1e3c2a-9d4b-5e7f-8a1c-2b3d4e5f6a7b", "status": "accepted", "receipt": "R-2026-000318", "document_ref_key": "a81c0d2e-7b8f-11f0-9c1d-00155d0a1b2c"}
```

Первый ответ — `202 Accepted`; повтор с тем же `X-Message-Id` — `200 OK` с **той же** квитанцией.

**4. Бизнес-ошибка:**

```json
{"message_id": "6f1e3c2a-9d4b-5e7f-8a1c-2b3d4e5f6a7b", "status": "rejected", "code": "SERIES_NOT_FOUND", "message": "Серия не найдена в базе 1С", "field": "item.series_ref_key"}
```

`422 Unprocessable Entity` — без автоповтора, сообщение уходит в карантин исходящих. Ошибка OData при чтении приходит «родным» телом 1С:

```xml
<m:error xmlns:m="http://schemas.microsoft.com/ado/2007/08/dataservices/metadata">
  <m:code>9</m:code>
  <m:message>Экземпляр сущности "ЭтапПроизводства2_2" не найден по переданному ключу.</m:message>
</m:error>
```

## 8. Подтверждения и обработка ошибок

Каждое исходящее сообщение получает квитанцию или ошибку; квитанция становится событием журнала (предварительно `erp.receipt.recorded` со статусом внутри — имена типов не кодируют результат, AD-40) и меняет ось «учёт в 1С» (AD-30).

| Класс ответа | Примеры | Поведение «Главного» |
|---|---|---|
| принято | `202` + квитанция | ось «учёт в 1С» меняется; строка очереди закрыта |
| повтор | `200` с той же квитанцией; OData код 15 «сущность с таким ключом уже существует» при детерминированном ключе | успех; двойного учёта нет (FR-31, FR-96) |
| бизнес-ошибка | `422` (`SERIES_NOT_FOUND` …); OData коды 4, 5, 16 (неверное значение, нет обязательного свойства) | без автоповтора → карантин исходящих, задача администратору; после исправления — ручная переотправка с тем же ключом |
| устаревшая ссылка | OData код 9 «экземпляр сущности не найден» | перечитать справочник, затем ручная переотправка |
| конфликт версии | `409`; HTTP 412 при `If-Match: DataVersion` | перечитать задание, ограниченный повтор |
| несовместимость контракта | OData коды 0, 3, 8 «тип сущности не найден», 10–12; расхождение `$metadata` с манифестом | канал `degraded`, отправка остановлена, карточка «чего нет» (кейс §6.2, критерий О8) |
| ошибка адаптера | OData коды 1, 2, 6, 7, 13, 14, 19 | карантин, тревога разработчикам |
| отказ доступа | `401`, `403`; OData код 20 | канал на паузу, тревога администратору |
| транспорт | `503`, `5xx`, таймаут, разрыв; OData код 18 | автоповтор с экспоненциальной задержкой (1 с, 5 с, 30 с, 2 мин, 10 мин, далее 30 мин; до N попыток), затем карантин |
| потерян ответ | запись в 1С прошла, ответ не дошёл | повтор с тем же `X-Message-Id` возвращает ту же квитанцию |

Коды OData — по открытой документации 1С (проверено по документации); реакция на них и коды HTTP-сервиса `qc` — наше решение.

**Сверка ответной стороны.** При старте и по расписанию адаптер читает `$metadata` и сравнивает с манифестом `contracts/integrations/erp/1c/metadata-manifest.yaml` (ожидаемые сущности и поля: `Document_ЭтапПроизводства2_2.Статус`, ссылки `…_Key` и т. д.) и версию `qc.v1` расширения. Расхождение — канал `degraded` до того, как пойдут ошибки кодов 8/10 (AD-18).

## 9. Stand 1С: граница эмуляции (NFR-TEST-2)

**Что имитирует:**

- те же адреса, формат JSON OData v3 и тело ошибок `odata.error` с кодами 8, 9, 15 на подмножестве объектов: номенклатура, серии, склады, подразделения, заказы и этапы производства, поступления;
- HTTP-сервис `/hs/qc/v1/` с ключом идемпотентности и квитанциями `202 / 200 / 422 / 409 / 503`;
- собственное состояние в схеме `stand_1c`: учётные документы, созданные по нашим сообщениям, качество серий, склад, где числится изделие;
- страница `/stand/1c/` — показывает полученное «глазами 1С» (список документов, карточка этапа, журнал обмена) в стиле интерфейса 1С (FR-91);
- сбои, включаемые только со страницы тестовых сценариев через служебный порт stand-а: доля 5xx, задержка дольше таймаута, «потеря» ответа при успешной записи (проверка идемпотентности), дубль, несовместимые `$metadata` с переименованным полем (проверка критерия О8), конфликт `DataVersion`.

**Чего нет:** проведения документов и прикладной логики ERP (регистры, себестоимость, остатки), прав пользователей 1С, плана обмена `SelectChanges`, конверта EnterpriseData, реальных имён реквизитов (они — проектное предположение до сверки с `$metadata` базы предприятия).

**Где в коде:** `backend/internal/infrastructure/integration/erp/1c/` (клиент), `…/erp/1c/stand/` (stand), роль `stands` процесса `ant`.

## 10. Путь к реальной 1С

1. Установить в базу 1С расширение конфигурации «КонтрольКачества» с HTTP-сервисом `qc` по спецификации `qc.v1`: регистр входящих сообщений (ключ идемпотентности → квитанция), заполнение документов по правилам ERP, ответы по §8.
2. Опубликовать нужные объекты в стандартном интерфейсе OData (состав задаёт администратор 1С) и завести пользователя с правом удалённого доступа.
3. Сменить адрес канала в `deploy/config/ant.yaml`, положить учётные данные файлом в том; адаптер при старте сверит `$metadata` с манифестом и покажет расхождения.
4. Для базы за корпоративной шиной (таблицы обмена) — тот же порт учёта, транспорт «таблица / каталог обмена»; при необходимости — конверт EnterpriseData с расширением формата в собственном пространстве имён и квитированием `MessageNo` / `ReceivedNo`.

Правила домена, порт учёта и контракт событий при этом не меняются (кейс §3.1: локализация изменений при замене внешней системы).
