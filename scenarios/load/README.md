# scenarios/load — нагрузочный прогон и проверки «1 = N» (эпик 35)

FR-107, FR-112, AD-6, SM-3; критерий кейса О6 «Масштабируемость». Описание узких мест и
измерений — [docs/scaling.md](../../docs/scaling.md).

## Запуск

```bash
make load                         # MS-1, N=4 воркера, сбой копии воркера на 20 с во втором прогоне
make load N=8 SCENARIO=S14 OUTAGE=0
```

`make load` собирает образ `ant:load` из рабочей копии (если его нет; `LOAD_BUILD=1` —
пересобрать), поднимает отдельный проект compose `ant-load` на портах 8484/8494
(демо-стенд на 8480/8491 не трогается) и делает два раздельных прогона одного
сценария с одним seed, каждый на чистой БД:

| Прогон | Состав | Что проверяет |
|---|---|---|
| `workers-1` | `ant` (api, стадия, проектор, планировщик, outbox, stands, security) + `ant-worker ×1` | эталон |
| `workers-N` | то же + `ant-worker ×N`; через 30 с одна копия воркера падает и через `OUTAGE` с поднимается | масштабирование и недоступность: партиции уходят живым копиям по истечении аренды (10 с) и возвращаются после подъёма |

Генератор интенсивности — пульт сценариев (эпик 32): события источников идут в
обычный приём без пауз (режим `load`, скорость ×1000), решения людей подписывает
demo-signer; шум генератора даёт опоздания, повторы, конфликты и потери источников.
Параметры профиля `load` (64 партиции, параллелизм свёртки 4, пачка 1024,
`synchronous_commit=off`) заданы переменными `ANT_*` поверх профиля `demo`: пульт
живёт на часах scenario и демо-персонах, которые есть только в demo.

## Что в отчёте

После каждого прогона разовая роль `ant -role=load` ждёт, пока воркеры, стадия и
проектор догонят журнал, и пишет `scenarios/load/out/‹прогон›.json`:

| Поле | Что |
|---|---|
| `duration_s`, `journal.facts_per_s` | длительность прогона и пропускная способность приёма |
| `latency_ms` | факт изделия → первая реакция движка на него (реальное время фиксации): p50, p95, max |
| `ingest.received / accepted / duplicates / quarantined / conflicts / gaps` | повторы (дубли гасятся идемпотентностью), конфликты содержимого, карантин, пропуски номеров источников (потери) |
| `completeness` | изделия прогона, из них «обработка остановлена», фактов на изделие |
| `hashes.state_hash` | итоговое состояние: свёртка каждого изделия, `engine.StateHash` без seq, basis_seq и времени записи |
| `hashes.rebuild_hash_1 / rebuild_hash_n` | пересборка всех проекций над тем же журналом на 1 и на N параллельных обработчиках (изделия делятся по партициям) |
| `board_hash`, `board_actual_hash` | табло автосверки: статусы и полученные значения строк |

Проверки `make load`: `rebuild_hash_1 = rebuild_hash_n` в каждом прогоне; `state_hash`,
`board_hash`, `board_actual_hash` прогона `workers-1` = прогона `workers-N`.

Роль `load` можно запустить и отдельно над готовой БД: `ANT_LOAD_RUN_ID=‹run_id›`
(без `ANT_LOAD_SCENARIO`) — только хеши и счётчики существующего прогона.
