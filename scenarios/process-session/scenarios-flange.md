# Сценарии на фланце люка с ожидаемыми результатами

> Черновик, пользователь его ещё не утвердил.
> **Все изделия, числа, режимы, ID, даты, поставщики и люди — условные.** Это не данные «Энергии».
> **[ПП]** — проектное предположение (режимы, камеры, оборудование на реальном производстве не проверены). **[П]** — наше допущение, его можно пересмотреть.
> Имена событий — из `process-events-catalog.md` (номер Е-.. + техническое имя). **Окончательные имена событий и полей задаёт контракт соседей** (их FR-27, FR-28, FR-90).

## 0. Коротко

1. Здесь 22 сценария на фланце люка гермокорпуса и пример обмена с 1С. S18–S22 — нестандартные случаи (§14). Они нужны соседям для имитатора цеха и для «табло проверки», где каждый сценарий показывает «ожидалось → получилось».
2. **Главная история демо — один связный поток «плохой день ИС-2»** (ИС-2 — сварочный источник на посту 2). Он идёт с понедельника 21.09 по четверг 24.09. В него входят S01–S09 и первая часть S10.
3. S11 («забыли прокладку»), S12 (испорченные сообщения), S15 (часы источника спешат), S16 (ненадёжная привязка к операции) и S17 (исполнитель отметил пропуск проверки) идут в том же потоке фоном, но в 4 минуты защиты не входят. Вторая часть S10 (лимит переделок участка шва) — отдельный короткий прогон. S13 («специалист заснул»: очередь на закрывающей точке без решения) — отдельный прогон в пятницу 25.09, после главной истории. S14 («общий фактор — один сварщик») — отдельный прогон в своём мире, 29–30.09.
4. Масштаб — десятки деталей: задание 1С на 40 фланцев, плюс 24 фоновых фланца прошлого заказа. Круг подозреваемых деталей тает так: **34 → 13 → 6**.
5. Каждая карточка устроена одинаково: цель → какие ситуации кейса закрывает → события по шагам → что должно получиться → чего не должно случиться.
6. Машиночитаемые ожидания лежат **отдельно от событий** — в `scenarios-flange-expected.yaml` (так требует кейс §5.1).
7. В 1С уходит только учёт на закрывающих точках (ЗТ). В главной истории это, среди прочего, «6 в брак» и «1 возврат поставщику». После удачной переделки изделие выходит из брака «возвратом из брака в производство» [П]. «Выпуск годного» уходит только после окончательной приёмки (ЗТ-6). Кейс §3.3 требует ещё «отправку результата контроля» — наше предложение в §6.5 [П], ждёт решения соседей.
8. Подпись в прототипе — как решили соседи. Основной путь — агент токена (их FR-69). Равноправный путь — подпись на бумаге (FR-139): документ печатают с QR-кодом, подписывают ручкой, скан загружают, и этот скан заверяет своей подписью второй сотрудник. В автопрогоне сценариев подписывает demo-signer. Любая подпись попадает в неизменяемый журнал.
9. В главную историю вплетены шесть ходов: эталонный фланец для сравнения; «уверенность ≠ качество» в числах; гипотеза про сварщика слабеет по фактам; опоздавший журнал сужает круг; переделка помогает не всем; в конце — что видит каждая из пяти ролей (§5) и таблица «требование кейса → где показано» (§8).
10. Для решений «ремонт» и «как есть» по уже изготовленному изделию нужен документ **«разрешение на отклонение»** (ГОСТ Р ИСО 9000, п. 3.12.5). «Разрешение на отступление» выдают до изготовления — в этих сценариях его нет.

Изделие начинается с выдачи заготовки (Е-09). С партией его связывает скан при выдаче, с инцидентом — блок и сообщение о решении.

Сценарии сверены со схемой v0.3 (`flange-process.bpmn`, `bpmn-v03-changes.md`): точки ЗТ-СР и КТ-СР, процессы «Сигнал», «Разбор причин», «Сбой оборудования». Список — §11.

Фон S08: скол, вмятина, царапина, геометрия — по одному сигналу, два подтверждены, два отклонены.

## 1. Как читать

**Четыре разных статуса — четыре разные записи.** Их нельзя смешивать.

| Статус | Кто ставит | Пример |
|---|---|---|
| 1. Сигнал о признаке дефекта | Система по данным камеры, рентгена, журнала станка | «Камера видит признаки прожога» |
| 2. Подтверждённое несоответствие | Контролёр ОТК | «Да, это прожог, деталь не соответствует чертежу» |
| 3. Предполагаемая причина (гипотеза) | Система предлагает, технолог уточняет | «Вероятно, сварочный источник: ток выше уставки» |
| 4. Подтверждённая причина или ошибка | Технолог, комиссия; ошибка человека — только после его письменного объяснения | «Причина — дрейф тока ИС-2, проверено контрольным образцом» |

**Три исхода любой проверки:** признаки обнаружены / признаков нет / **оценка невозможна**. Плохой кадр — это «оценка невозможна», а не «годно».

**Цвета деталей в области риска** (всегда с подписью): красный — подтверждено; жёлтый — под подозрением, **это ещё не брак**; зелёный — исключено из инцидента; серый — нет данных.

**Слои событий:** Ф — факт из цеха; В — вывод системы; Р — решение человека; И — обмен с 1С.

**Время.** Время события — когда оно случилось. Время получения — когда система его приняла. История строится по времени события. Всё время — местное, МСК.

**Сокращения.** КТ — контрольная точка; ЗТ — закрывающая точка (деталь стоит, пока человек не подтвердит решение); ОТК — отдел технического контроля; РК — рентгеновский контроль; КИМ — координатно-измерительная машина; НС — несоответствие; ПЗ — представитель заказчика; МЦ, СЦ, СИЦ — механический, сварочный, сборочно-испытательный цех.

Маршрут: входной контроль → мехобработка → сварка фланца с кольцом → сборка с **установкой оборудования** (клапан КВД в штуцер крышки — кейс §1.1) → испытание на герметичность → окончательный контроль ОТК → склад.

**Маркировка** [П, версия 0.3]. До мехобработки на заготовке фланца — бирка на таре: станок срезал бы код. Код DataMatrix наносят после мехобработки на нерабочую поверхность по КД — это перемаркировка «бирка → код». ОТК сверяет номер на ЗТ-2. Код не читается — ручная привязка с пометкой «надёжность низкая» (Е-101). На КИМ номер считывают с кода, без сканера — выбирают из списка ожидаемых изделий, а не вводят руками.
Рентген шва — **обязателен по КД** [П]. ПЗ подписывает на окончательном контроле (ЗТ-6) и при решениях «ремонт» или «как есть» по разрешению на отклонение [П].

**Линии** [П]. Кейс просит поле линии, справочник линий, разрез «дефекты по линиям» и экран «состояние линии» (§1.4, §2.4, §4.3, §4.4). В наборе две линии:

| Линия | ID | Свой участок | Общие участки обеих линий |
|---|---|---|---|
| Линия ФЛ-100 № 1 | `L-FL-1` | Сварочный пост 1: источник ИС-1, шлюз ШЛ-1, терминал поста | Входной контроль, ЧПУ-1 и КИМ-1, пост ЗТ-3 с камерами КТ-3, рентген, сборка, стенд, окончательный контроль, изоляторы, кладовые |
| Линия ФЛ-100 № 2 | `L-FL-2` | Сварочный пост 2: источник ИС-2, шлюз ШЛ-2, терминал поста | То же |

Почему так. Сварка — единственный сдвоенный участок маршрута и спецпроцесс, на котором случился инцидент. Одна линия дала бы пустой разрез «по линиям». Две линии по постам дают честный разрез: дефекты главной истории делятся по постам, где сварен шов (§7).

Какая линия у события:
- событие поста (его терминал или сварочный источник) — линия этого поста;
- событие по фланцу с момента запуска — линия поста, где сделана его последняя сварка. До первой сварки — линия из плана запуска [П];
- переварка на посту другой линии переводит фланец на эту линию. В четверг пять фланцев переваривают на посту 1, и дальше они идут по линии 1;
- без линии: сообщения 1С и КОМПАС, партии и компоненты на складе, общее оборудование без номера изделия (ЧПУ-1, ключ, стенд в своих журналах).

Все характеристики оборудования — [ПП]. Важные условные числа:
- **уставка тока сварки — 160 ± 10 А** [ПП]; ИС-2 во вторник «уплыл» до **182 А**;
- шов идёт по отверстию фланца Ø 250 мм (π × 250 ≈ 785 мм) и делится на **8 участков по ≈ 98 мм: У1…У8** [ПП];
- переделка одного участка шва по ТП — **не больше 3 раз** [ПП]; окно от подготовки кромок до сварки — **не больше 8 ч** [ПП];

### S13. «Специалист заснул» — очередь на ЗТ-3 без решения

**Цель.** Показать, что будет, если на закрывающей точке никто не принимает решения. Детали копятся перед точкой. Живая карта показывает растущую очередь и новое узкое место. Система **не пропускает детали сама**: без подписи человека дальше нельзя. Вместо этого срабатывают сроки и эскалация с «ценой задержки». Мастер перераспределяет работу, очередь рассасывается. **Закрывает.** §2.4 кейса — дополнительные показатели «ожидание» и «простой»; §1.2 — мастер отслеживает задержки, руководитель — время обработки; §5.2 — изделия, которые стоят на ЗТ без подписи (О-9). **Правило** [П]. Время события позже времени приёма больше чем на 30 с — часы источника спешат. Сдвиг = медиана (время события − время приёма) по записям источника + обычная задержка доставки. Исправленное время = время события − сдвиг. Часы, которые отстают, похожи на задержку доставки — их ловит сверка времени edge-агентом [ПП].

**Что должно получиться.**
- У пяти протоколов КИМ (Ф-007…Ф-011) — исходное время как есть и рядом исправленное, с пометкой «время исправлено по правилу: часы источника +7 мин».
- Порядок записей КИМ-1 по номерам не нарушен; ничего не переставлено и не отброшено.
- В истории этих фланцев протокол КИМ стоит до подписи ЗТ-2.
- Администратор видит сдвиг с 08:25, синхронизирует часы в 10:15; следующая запись (Ф-013) — без поправки.
- Качество потока (Н-5): «время исправлено по правилу» — 5 записей, источник КИМ-1.

- В показателях ожидания нет отрицательных интервалов «КИМ → ЗТ-2».


**Правила обмена** (исполняют соседи):
- **Что уходит.** Только учётные движения на ЗТ: «принято в работу», «перемещение», «перевод в брак (переделка)», «возврат из брака в производство» [П], «перевод в брак (списание)», «возврат поставщику», «выпуск годного». «Выпуск годного» — только после подписанной ЗТ-6. Изделие, переведённое в брак на переделку, выходит из брака только «возвратом из брака в производство» после повторной ЗТ того блока, где его переделывали (ЗТ-2, ЗТ-3, ЗТ-4 или ЗТ-6). Предложение по «результату контроля» — §6.5.
- **У каждого сообщения есть ответ.** Подтверждение (с номером документа 1С) или ошибка. Статус «учтено в 1С» — только после подтверждения.
- **Отправка не держит изделие.** Изделие идёт дальше по своей подписи на ЗТ; «учтено в 1С» — отдельный статус.
- **Ошибки.** Временная ошибка (5xx, нет ответа) — повтор с паузой и с тем же номером сообщения, поэтому 1С не проведёт документ дважды (S01: 503). Ошибка данных (4xx) — без автоповтора, задача администратору; после исправления — повтор с тем же номером (S02: 422).
- При воспроизведении истории в 1С ничего не отправляется.
- Для Галактики:ERP, MES и КОМПАС-3D — те же правила, форматы — в заготовках адаптеров соседей.

### 6.5. Предложение: сообщение «результат контроля» [П, ждёт решения соседей]

Кейс §3.3 дословно просит «отправку результата контроля». Учётные движения выше этого не закрывают: они говорят, куда делось изделие, а не что показал контроль. Предлагаем отдельное сообщение «результат контроля». Окончательно решают соседи (имя, поля, когда уходит); в данных имитатора его нет, в ожиданиях оно помечено `proposal` (I1-08, I1-09, I1-N5).

**Когда уходит.** После каждой подписанной закрывающей точки: ЗТ-1 — по партии, ЗТ-2…ЗТ-6 — по изделию; после решения ЗТ-Р. Одно сообщение на одно решение. Сигналы, решения по сигналам и сужение круга — не повод.

**Что в нём.**

| Поле | Пример (Ф-001, ЗТ-6) |
|---|---|
| Номер сообщения, версия контракта | `qc-out-000120`, `1.0` |
| ЗТ и номер предъявления | ЗТ-6, первое |
| Изделие или партия; заказ; номенклатура (ID 1С) | `ser-91d0-0001`; `ord-5c2b-0917`; `nom-7a1e-0001` |
| Линия | `L-FL-2` |
| Итог | годно / годно по разрешению на отклонение № … / не годно |
| При «не годно» | номера НС, кратко дефекты (класс, зона, тяжесть), решение по изделию |
| Когда и кто подписал | Ср 23.09 10:15; ОТК-2, ПЗ-01 |
| Основание | наши ID записей; сами кадры и журналы остаются у нас |

**Чего в нём нет.** Сигналов, гипотез, кадров, журналов станков, круга подозреваемых.

**Ответ 1С** — как у учётных сообщений: подтверждение, ошибка, повтор с тем же номером. Сообщение не держит изделие и не заменяет учётное движение. В 1С:ERP ему ближе всего «акт контроля качества», в 1С:MES — «предъявление на контроль» (см. `research/erp-1c-galaktika.md`).
