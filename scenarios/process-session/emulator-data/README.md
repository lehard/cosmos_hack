## 2. Строка потока (JSONL)

```json
{"event_id":"…uuid…","event_type":"machine.state","schema_version":"1.0","source_id":"WS-2","source_seq":1695,
 "source_kind":"machine","occurred_at":"2026-09-22T07:20:14.000Z","received_at":"2026-09-23T09:05:07.000Z",
 "recorded_at":null,"line_id":"L-FL-2","payload":{"equipment_id":"WS-2","state":"warning","code":"WELD_CURRENT_HIGH",
 "parameter":"welding_current_a","value":176,"setpoint":{"nominal":160,"tolerance":10,"unit":"A"},…},
 "_sim":{"gen_no":6149,"label":"EV-WS2-0412","scenarios":["S05","S06","S07","S09"],"process":null,"noise":"late",
 "sign_via":"edge-agent","edge_agent":"GW-2"}}
```

**Конверт.**
- `event_id`, `event_type` (наше имя), `schema_version` (версия контракта `1.0`; отдельно от `analyzer_version`), `source_id`, `source_seq`, `source_kind`.
- Три времени:
  - `occurred_at` — когда событие случилось;
  - `received_at` — **плановое** время доставки по доменным часам сценария. Имитатор отдаёт строку в этот момент, ядро ставит своё время приёма;
  - `recorded_at` — всегда `null`, его ставит ядро.
- Время в UTC, RFC 3339, ровно три знака миллисекунд. На экране — МСК (+03:00).
- `occurred_at` — время **по часам источника**, как он его прислал. В S15 часы КИМ-1 спешат на 7 мин: у пяти строк `occurred_at` позже `received_at` (`_sim.noise = clock_skew:+7m`). Исправлять — дело ядра; в файле значение исходное.
- `item_id` — для событий по изделию, `line_id` — линия (правило ниже), `lot_id` — по партии, `correlation_id` — обычно `operation_run_id`, дальше `payload`.

**Линия (`line_id`)** [П]. Линий две: `L-FL-1` и `L-FL-2` (`sites.yaml → lines`). Они расходятся только на сварке: у каждой свой сварочный пост, остальные участки общие.
- Источник поста (терминал `TERM-WS-n`, сварочный источник `WS-n`) — всегда линия своего поста, даже без изделия (сводки тока, контрольный образец CS-07).
- Событие по фланцу (`item_id` F-…) с момента запуска (`item.registered`) — линия поста, где сделана его последняя на этот момент сварка. До первой сварки — линия из плана запуска. Переварка на посту другой линии переводит фланец на эту линию: в Чт 24.09 пять фланцев переходят на линию 1.
- Без линии: 1С и КОМПАС, партии и компоненты на складе (в том числе маркировка заготовок до запуска), общее оборудование без `item_id` (ЧПУ-1, ключ, журнал стенда), сообщение S12 без `item_id`.
- В `operation.started` поля `line_id` в `payload` больше нет: линия — в конверте.

**`_sim` — метаданные генератора.** Перед подписью и приёмом их нужно отрезать, в журнал они не идут:
- `gen_no` — номер события генератора;
- `label` — ASCII-метка для ссылок из шагов и ожиданий, например `EV-WS2-0412`, `kt3/SV-017-1/CAM-WS-1`;
- `scenarios` — к каким сценариям относится строка;
- `process` — экземпляр процесса схемы v0.2, которому принадлежит факт, или `null` (правило ниже) [П];
- `process_links` — другие экземпляры, которым этот факт нужен как сообщение (например, выдача со склада — изделию) [П];
- `noise` — вид шума: `late`, `duplicate`, `malformed:<код>`, `conflict:E_ID_CONFLICT`, `edge:…`;
- `sign_via` — кто подписывает;
- `edge_agent`;
- `persona` — только для терминалов;
- `after_step` — строку отдавать только после этого шага человека;
- `note`.

**Экземпляры процессов (схема v0.3)** [П]. В схеме девять процессов, общих фишек нет (`process/bpmn-v03-changes.md`, `sites.yaml → bpmn_processes`). Ключ экземпляра — деловой ключ объекта:
- `order/<order_id>` — «Заказ из 1С»; первая строка — `erp.order_received` (Е-01);
- `lot/<lot_id>` — «Партия»; первая строка — `erp.batch_received` (Е-03). Сюда же входной контроль, маркировка заготовок и колец **до запуска**, компоненты на складе (рентген колец К-104, К-105) и выдача со склада (`batch.issued`);
- `item/<item_id>` — «Фланец в сборе»; первая строка — `item.registered` (Е-09, выдача заготовки). Всё по фланцу после неё — в этом экземпляре. `process_links` у Е-09 — заказ и партия заготовки; у выдачи со склада — изделия, под которые выдано;
- `incident/<RS>`, `review/<ЗТ>/<изделие>`, `nc/<НС>` — «Инцидент», «Пересмотр приёмки», «Решение по несоответствию». Их начинают реакции движка, поэтому в потоках их нет — только в шагах людей (`process_ref`, `process_links`);
- `signal/SG-<основание>` — «Сигнал» (схема v0.3), один экземпляр на сигнал: шаги подтверждения и отклонения (Е-90, Е-91); реакции Е-80, Е-84 — только в ожиданиях;
- `cause/<RS>` — «Разбор причин и корректирующие действия» (v0.3): П-04, П-05…П-07, П-09, П-10 (S02 — RS-02, S05 — RS-01, S14 — RS-14);
- `equipment/<метка>` — «Сбой оборудования, нарушение режима, пропуск проверки» (v0.3), один экземпляр на событие: предупреждения источника (Е-43), пропуск проверки (Е-21), ручное вмешательство (Е-22), запись пульта станка без номера выполнения (S16). Это строки потока; изделие — в `process_links`;
- `null` — сводки и состояния оборудования без `item_id` (к изделию их привязывает стадия AD-29), КОМПАС и номенклатура, контрольные образцы CS-07 и CS-141…143, сообщение S12 без `item_id`.

Порядок выдач по схеме: кольцо (V6) выдаётся после приёмки фланца сварочным цехом и до скана фланца с кольцом (WJ, Е-41); скан — до подготовки кромок (W1); комплект на сборку (V7) — после приёмки сборкой. Исключение, которое схема допускает, — S13: в Пт 08:10 комплекты выданы по сменному заданию до прихода изделий, шаг V7 закроется, когда изделие войдёт в сборку.

`_sim.process` — ожидание для проверки корреляции, а не поле контракта: ядро выводит экземпляр само по `item_id`, `lot_id`, `order_id`. Поэтому поле лежит в `_sim` и формат конверта не меняется.

**Подписей нет.** Подписывает `edge-agent` (устройства и камеры) или `stand` (1С, импорт КОМПАС). Терминалы рабочих мест (`sign_via: terminal`) — это ручной ввод исполнителя с подписью уровня 1. В автосверке его подписывает demo-signer под персоной `_sim.persona`, в интерактивном режиме — агент токена. Это вопрос к соседям (§7, вопрос 1).

**ID.** В файлах `event_id = UUIDv5(NS_TEMPLATE, "<stream_id>:<seed>:<gen_no>")`. В прогоне соседи пересчитывают его по AD-38: `UUIDv5(run_id, seed ‖ gen_no)`, а `source_id` превращают в `‹run_id›/‹source_id›`. У дубля тот же `gen_no`, поэтому тот же `event_id` и тот же `source_seq`. `source_seq` идёт с 1 на каждый источник в каждом прогоне. Разрывы есть только там, где они объявлены в `streams/_manifest.yaml → gaps`.

**Что в потоках, а что нет.**
- **В потоках** — только исходные факты:
  - цех: терминалы, станки, камеры, стенды, ключ, рентген, OperatorVision;
  - вход из 1С и импорт КОМПАС.
- **Решения людей в потоки не входят.** Это ЗТ, подтверждение и отклонение сигнала, изоляция, решение по изделию, сужение круга, причина, остановка источника, назначения на пост. Они лежат в `definitions/scenarios/*.yaml → human_steps` с временем, ролью, персоной, подписантами, `mode` и `expect`:
  - `mode: stop` — сценарий ждёт решения на столе роли;
  - `mode: auto` — demo-signer подписывает сам;
  - `expect` — `accepted` или `refused:<код>`.
- **Выводы движка в потоках тоже нет.** Это сигналы, карантин по правилу, область риска, гипотезы, «нет данных», исходящие в 1С, метка «пересмотрите» (`decision.review_flagged`, Е-122 [П]), сообщение о решении каждому изделию (узел I7), `gate.wait_overdue` и `escalation.closed`. Они проверяются только ожиданиями.

## 5. Как это грузится

1. **Генезис и нормативный слой** (их `ant init`, AD-31, AD-33). Справочники из `definitions/reference/` становятся записями `reference` с `valid_from`: люди, роли, полномочия и клейма; оборудование и поверка; календарь и смены; партии; карты контроля; правила. Таблицу соответствия 1С получает stand 1С, **кроме** договора SUP-3: его добавляют шагом в сценарии.
2. **Имитатор / stand-ы / edge-агент** (AD-26).
   - Строки отдаются по порядку `received_at` на доменных часах сценария; пауза останавливает поток и часы.
   - Перед подписью `_sim` отрезается, к `source_id` добавляется префикс прогона, `event_id` пересчитывается по `gen_no`.
   - `source_seq` из файла берётся как есть — иначе не воспроизвести дубли и разрыв.
   - Строка с `_sim.after_step` ждёт, пока выполнен шаг с этой меткой.
   - Строки S12 специально нарушают контракт: они должны дойти до приёма как есть.
3. **Шаги людей** (`human_steps`).
   - `stop` — в интерактивном режиме сценарий ждёт на столе роли; в автосверке demo-signer подписывает запрос, совпадающий с шагом.
   - `auto` — demo-signer подписывает сам в `at`.
   - Шаги с `expect: refused:…` проверяют отказы: сужение круга контролёром, отклонение без причины, исправление записи «на месте», переделка сверх лимита, ремонт без разрешения на отклонение.
   - Шаги с `optional: true` нужны только при названном условии.
4. **Сбои stand-а 1С и подделка** — из `stand_faults` и `tamper_actions` через служебный порт stand-а и `cmd/tamper`.
5. **Адаптер заготовок (FR-150, AD-36).** Их генератор строит `scenarios/fixtures/<сценарий>/steps/NN.yaml` из тех же потоков, шагов и seed, поэтому ID изделий совпадают с прогоном. Ответы по `operationId` берутся из `expected/*.yaml`. Соответствие наших `subject`/`field` их `operationId` и путям ответа — открытый вопрос (§7, вопрос 2).
6. **Табло** (FR-108) сверяет `expected/*.yaml`. Это наш YAML без изменений, времена в МСК. Утверждения с полем `proposal` — наше предложение, которое ждёт решения соседей («результат контроля»): показывать «ждёт решения соседей», а не «не выполнено».
7. **Пересобрать и проверить:**

   ```
   python3 tools/generate.py && python3 tools/split_expected.py && python3 tools/check.py
   ```
