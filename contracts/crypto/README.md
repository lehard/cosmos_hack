# crypto — формат подписанного пакета и кодирование (AD-10, AD-32, AD-44)

## Пакет

Всё подписываемое — конверт **DSSE v1** (`dsse-envelope.schema.json`) над каноническим JSON (RFC 8785, JCS):

- `payloadType` = `application/vnd.ant.‹класс›+json; v=‹версия›` — классы в `payload-classes.yaml`; ключ подписывает только классы из своего акта регистрации.
- `payload` = base64 (стандартный алфавит, с `=`) канонических байтов содержимого.
- подпись — над **PAE**: `"DSSEv1" SP LEN(payloadType) SP payloadType SP LEN(payload) SP payload` (длины — десятичные, в байтах; payload — сырые байты, не base64).
- `signatures[].keyid` = `key_id@версия`; у профиля `hybrid` — две подписи (ГОСТ и ML-DSA-65) разными ключами одного субъекта; лишние и повторные подписи не засчитываются.

Под подписью, внутри payload (кейс §6.3, FR-67): версия формата, id криптопрофиля, `key_id@версия` каждого подписанта, перечень обязательных подписей, ссылка на исходное событие или материал, открытые параметры проверки — для событий это блок `integrity` конверта (`events/common/envelope.v1.json`).

**Канонический вид (AD-10).** Подписываемые байты обязаны совпадать с каноническим видом своего разбора: без повторяющихся ключей; только целые в пределах ±(2^53−1) (большие — строками; float в контрактах нет); строки в NFC; идентификаторы — ASCII по шаблону. Иначе — `ingest.canonical_form_violation`. JCS в Go — `encoding/json/jsontext` `Value.Canonicalize`; в JS — рекурсивная сортировка ключей по UTF-16 + `JSON.stringify` (для нашего подмножества без float это и есть RFC 8785).

## Профили (`profiles.yaml`)

| Профиль | Алгоритм | Кодирование |
|---|---|---|
| `gost` | ГОСТ Р 34.10-2012, 256 бит, `id-tc26-gost-3410-12-256-paramSetA`; хеш — Стрибог-256 | см. ниже |
| `pq` | ML-DSA-65 (FIPS 204), контекстная строка `ant/‹payloadType›`; демонстрационный | открытый ключ — 1952 байта FIPS 204; подпись — 3309 байт; base64 |
| `hybrid` | обе подписи обязательны | две записи в `signatures` |

### ГОСТ Р 34.10-2012 — точное кодирование

- **Дайджест.** `h = Стрибог-256(PAE)` — 32 байта в порядке `hash.Sum()` (GoGOST `gost34112012256`; для сообщения `"012345678901234567890123456789012345678901234567890123456789012"` это `9d151eef…5500`).
- **Число e.** По стандарту `e = α mod q`, где α — число, чьё двоичное представление — вектор h. Байты `hash.Sum()` записаны младшим разрядом вперёд, поэтому α = **little-endian** интерпретация 32 байт дайджеста. В GoGOST — обёртки `gost3410.PrivateKeyReverseDigest` / `gost3410.PublicKeyReverseDigest` (разворот дайджеста перед `SignDigest`/`VerifyDigest`).
- **Подпись.** 64 байта `s ‖ r`, каждое — 32 байта **big-endian** (как возвращает GoGOST `SignDigest`); в JSON — base64.
- **Открытый ключ.** 64 байта `X ‖ Y`, каждое — 32 байта **little-endian** (GoGOST `PublicKey.RawLE()`, как OCTET STRING в сертификатах по RFC 4491); в JSON — base64; отпечаток ключа — `streebog256:` + hex(H(64 байта ключа)).
- Закрытых ключей нет ни в пакете, ни в коде, ни в демо-наборе; в тест-векторах — только специально сгенерированный тестовый ключ.

## Хеш формата цепочки v1 (AD-44)

`H` = Стрибог-256. Отпечатки, адреса материалов, звенья, `commit` в JSON пишутся как `streebog256:‹64 hex›` (hex — байты `hash.Sum()` по порядку). При склейке внутри формул используются **сырые 32 байта**. Формулы — `contracts/journal/chain-format.v1.md`. Смена H — новый сегмент цепочки (AD-32).

## Тест-векторы (`test-vectors/vectors.v1.json`)

Сгенерированы `test-vectors/generator` (Go 1.27.1, `github.com/deckhouse/gogost/v6` v6.2.0 — код GoGOST; `crypto/mldsa`; `encoding/json/jsontext`) в контейнере; команда — в шапке `generator/main.go`. Разделы: `streebog256`, `jcs`, `sample_event`, `dsse_pae`, `gost3410_2012_256` (подпись с фиксированным k, проверка, изменённый пакет → «не сходится»), `mldsa65` (детерминированная подпись, другой контекст → не проверяется), `dsse_envelope_hybrid`, `chain_v1` (две записи), `doc_digest` (AD-12), `merkle_rfc6962` (сменный рапорт, AD-12), `uuid5` (от `NS_ANT`).

**Эталонные документы** (`test-vectors/documents.v1.json`, AD-12): сопроводительная карта, заявление о несоответствии, решение по несоответствующей продукции — шаблон, канонический `content`, каноническая отрисовка HTML, `rendering_hash`, `doc_digest`, QR. Сервер (свёртка, `domain/documents.Compose`) и агент токена (пересчёт из `content` и шаблона того же коммита, `domain/documents.Rebuild`) обязаны получить их байт в байт — тест «отпечаток сервера = отпечаток агента» (`backend/internal/application/documents/golden_test.go`); раздел `doc_digest` файла векторов — независимая проверка самого правила (`domain/documents/digest_test.go`). Пересборка эталона — только вместе с новой версией шаблона или `doc_format_version`: `ANT_UPDATE_DOC_VECTORS=1 go test ./internal/application/documents -run TestGoldenDocuments`.

`contracts/scripts/check.sh` перепроверяет без ГОСТ-библиотеки то, что можно: JCS, PAE, UUIDv5, соответствие примера события и записей цепочки схемам. Стрибог и подписи проверяют Go-тесты эпика 05 (криптоядро) на этих же векторах — «отпечаток сервера = отпечаток агента» (AD-12).

## Смена профиля и ротация (AD-32)

Старые подписи не трогаются и проверяются по профилю на момент подписи; реестр профилей и ключей — записи `key.profile.registered`, `key.registration.recorded`, `key.revocation.recorded`. Недоступный ключ — «не проверяемо» (`signing.key_unavailable`), никогда не «валидно». Данные до и после смены ключа и профиля, изменённый пакет и недоступный ключ — `scenarios/crypto` (создаются при `ant init`, эпик 05).
